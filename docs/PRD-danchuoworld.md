## 1. Обзор и цели

Публичный персональный сайт-дашборд на собственном домене: «живая визитка» вокруг **календаря**, где центр — **текущий день** и его статистика, а вокруг — компактные виджеты (Spotify, проекты, соцссылки, тема). Часть данных приходит автоматически (Apple Health, Spotify), часть вводится в один тап через iOS-шорткаты. Визуальный стиль («волна») сменяем по релизам в честь периода жизни.

**Цели v1:**
- Рабочее ядро «Сегодня + календарь» без застреваний на трудных интеграциях.
- Автоматизировать дешёвые источники (Health через Shortcut, Spotify через API).
- Заложить архитектуру тем («волн»), расширяемого чеклиста и адаптива с первого дня.
- Минимальная приватная аналитика посещений на своём решении.
- Сложные хотелки (экранное время, велопоездки Велобайк, книги, плёнка, 3D) — высокоприоритетный бэклог, не блокируют релиз.

**Нецели v1:** геймификация, 3D-конвертация артефактов, админ-панель, загрузка фото через UI, ретроспективная история Spotify, публичный счётчик посещений, листание прошлых месяцев.

## 2. Целевая аудитория

- **Читатель (публичный):** любой посетитель домена. Только чтение. Видит публичный дашборд.
- **Владелец (один — ты):** единственный, кто пишет данные. Write-эндпоинты — только по токену. В v1 нет UI для записи (шорткаты + прямые вызовы API).

### 3.1. Архитектура расширяемости (open for extension)

> **Цель.** Бэклог (§9, §14) — это поток будущих «приколов»: новые источники данных, новые плитки, новые волны. Архитектура обязана принимать их **добавлением кода рядом**, а не переписыванием ядра. Принцип — open/closed: ядро закрыто на правку, открыто на расширение.

**Главное решение — feature-пакеты (вертикальные слайсы), без плагин-SPI.** Расцепленный монолит организуется не слоями (controllers/services/repos), а **по фичам**: каждая фича — самодостаточный пакет, владеющий своими сущностями, миграциями, REST-эндпоинтами, кэшем и конфигом. Расширение = **новый пакет по соглашениям**, существующие не трогаются. Формальный плагин-SPI / общие провайдер-интерфейсы (авто-дискавери самозапускающихся модулей) **сознательно не вводим** — для персонального монолита это over-engineering; границы держатся дисциплиной пакетов и сквозными соглашениями (§4, §11). Если появится несколько однотипных реальных источников (а не гипотетических) — формальный интерфейс выделяется тогда, по факту, а не наперёд.

```
backend/
  days/        DayRecord, агрегатор дня, GET /api/days*
  health/      Workout, ingest/health
  checklist/   ChecklistItem, ChecklistEntry, ingest/daily (отметки)
  monster/     MonsterFlavor (вкусы — data-driven)
  spotify/     OAuth, кэш, GET /api/spotify/*
  theme/       Theme (волны, токены JSONB), GET /api/theme*
  projects/    Project
  social/      SocialLink, Artifact (marquee)
  analytics/   AnalyticsEvent (бикон) + InteractionEvent (хитмапа кликов, B2)
  film/        FilmDrop, FilmPhoto, GET /api/drops* (каркас, загрузка — B1)
  llm/         LlmClient (текст + vision + vision-JSON) → Groq | Gemini по конфигу
  core/        сквозное: bearer-фильтр, рейтлимит, конфиг (MSK, генезис), общий кэш-вайринг
```

Новая фича (`ride/`, `film/`, `books/`, …) добавляется как ещё один пакет рядом — `core` и соседи не меняются.

**Швы уже заложены (data-driven, расширение без релиза).** Многие «приколы» — это не код, а **данные/конфиг**, и добавляются на проде без деплоя:
- **Пункты чеклиста** (`ChecklistItem`) и **вкусы монстра** (`MonsterFlavor`) — новые добавляются записью в БД (§5.6).
- **Волны** (`Theme`, токены **и опциональная раскладка** в JSONB) — новый визуальный стиль = новая запись; смена активной волны меняет весь сайт (визуал **и** композицию плиток) **без правок компонентов** (§5.9, DESIGN §10).
- **Проекты, соцссылки, артефакты** — наполняются сидом/API.

**Фронт — data-driven реестр тайлов (сквозной шов).** Bento-борд собирается не из захардкоженной разметки, а из **реестра плиток**: каждая плитка объявляет `{id, источник (endpoint), компонент, дефолтный layout {col,row,colSpan,rowSpan}}`. Новый виджет = **запись в реестре + компонент**; борд и соседние плитки не трогаются. Волна может **переопределять спаны и прятать плитки** (DESIGN §3.1, §10) — смена композиции под волну без правок компонентов (мерж дельты поверх дефолтного реестра). Per-tile состояния (loading/empty/error/loaded) и пустые слоты делают добавление/удаление плитки безопасным (DESIGN §7).

**Рецепт нового «прикола» (полный путь источника данных).**
1. **Backend:** новый feature-пакет → сущность + Liquibase-миграция → публичные `GET` → (если данные пушит телефон) идемпотентный `ingest/*` за токеном → кэш и его инвалидация при ingest — всё внутри пакета.
2. **Frontend:** запись в реестре тайлов + компонент плитки.
3. Соглашения соблюдаются по умолчанию: мутации за bearer, все GET публичны, ingest — upsert по дате (идемпотентность), канон MSK, ноль хардкод-токенов (§4, §11, DESIGN §2.5).

**Guardrail (важно для «открыт для расширения» ≠ «предзаготовить всё»).** Шов должен быть **дешёвым**, а не спекулятивной схемой под все мыслимые фичи. Сущности и эндпоинты **не создаются, пока нет реального канала данных** — каноничный пример — экранное время Apple (нет программного доступа → сущность/эндпоинт не заводим, только ручное поле `screenTimeMinutes`; §9 B-бэклог, риски §13). Расширяемость = легко добавить, когда канал появится, а не нести мёртвый код.

**Синхронизация с эрами разработки (§12).** Каждая эра устанавливает или проверяет конкретный шов; следующая опирается на него, не переделывая предыдущую:

| Эра | Что закладывается / проверяется по расширяемости |
|---|---|
| **M0** | Каркас feature-пакетов + `core` (bearer-фильтр, профили, конфиг MSK/генезис) и конвейер Liquibase — пустые швы и сквозные соглашения на месте. |
| **M1** | Первые вертикальные слайсы (`days`/`health`/`checklist`/`monster`) + data-driven сиды — доказано: новый пункт/вкус добавляется без деплоя. |
| **M2** | Фронт-**реестр тайлов** + спаны через layout-конфиг (DESIGN §3.1) — новая плитка = запись + компонент. |
| **M3** | `spotify` как изолированный слайс с внешним OAuth/кэшем — доказывает, что внешний источник живёт в своём пакете, ядро не трогается. |
| **M4** *(готово)* | `theme`/`analytics`/`projects`/`social`/`film` слайсы; волна переопределяет токены **и раскладку** (переставить/спрятать плитки) без правок компонентов (SSR-инжект + клиентский своп) — полный цикл расширяемости волной. |
| **M5** *(готово)* | Регрессия швов: пустой слайс/тайл и пустые слоты не ломают борд (пустые/будущие состояния) — пройдено аудитом + визуальной регрессией; новый слайс свежести (`lastIngestAt`) добавлен по рецепту, ядро не тронуто. |
| **B-фазы** | Каждый бэклог-«прикол» (велопоездки, плёнка, книги, экранное время) приземляется по рецепту выше — новый слайс + тайл, ядро неизменно. |

## 4. Семантика данных и времени

> Сквозные соглашения, обязательные для корректности. Решить до M1.

- **Канонический часовой пояс — MSK (UTC+3).** Все «дни», границы суток, агрегаты считаются в MSK независимо от tz сервера/посетителя. *(Будущее: переключатель смещения автором — улетел в другой пояс, на сайте везде показывается сдвиг.)*
- **Граница суток** — полночь MSK.
- **Сон относится ко дню пробуждения.** Смотрим 15-е → показываем сон, из которого проснулся 15-го (засыпал 14-го). `sleepMinutes` дня D = сессия сна, завершившаяся (пробуждение) в день D. Решение подтверждено владельцем 2026-07-28 при сверке с Health (альтернатива — конвенция Apple — рассмотрена и отклонена).
  - ⚠️ **С Apple Health это расходится ровно на сутки, и это не баг.** Health подписывает ночь **вечером засыпания** (окно 18:00 → 18:00), мы — **утром пробуждения**, поэтому `дата у нас = дата в Health + 1` при любом нормальном ночном сне. Практическое следствие для ручного досыла (Приложение А.2.1): в шорткате выбирается **день пробуждения**, а не то число, под которым ночь лежит в приложении Здоровье. Особенно заметно, когда засыпание происходит после полуночи: сессия целиком лежит внутри одних суток, у нас она этими сутками и подписана, а Health отдаёт её предыдущим днём.
- **Дневник относится ко дню, чей вечер идёт** — окно `[D 19:00, D+1 02:00)` MSK (§5.6). Запись в 00:40 закрывает **уходящий** день, а не начинает наступивший.
  - ⚠️ **Это противоположно правилу сна, и обе стороны верны.** Сессия в 01:00 у сна уходит в **наступивший** день (день пробуждения), у дневника — в **уходящий**. Разница не в реализации, а в смысле события: сон — это то, чем день начался, дневник — то, чем предыдущий кончился. Полночь не граница ни там, ни там. Практическое следствие для ручного досыла: **дата запроса на раскладку дневника не влияет вовсе** — минуты раскладываются по вечерним корзинам сами, поэтому досылать надо по-прежнему день **пробуждения** (ради сна), а дневник встанет на своё место.
- **Генезис-дата danchuo.world** — фиксированная дата отсчёта в конфиге. Данные хранятся и показываются с неё; раньше — пусто.
- **Будущие дни** в календаре рендерятся пустыми.
- **Все данные публичны** — осознанное решение владельца.

## 5. Основные функции v1

Каждая фича: описание → acceptance criteria → technical considerations.

### 5.1. Каркас экрана (bento-сетка)
**Описание.** Главный экран — bento-сетка модульных плиток, центр — крупная плитка «Сегодня». Рассчитан на 16" (~1512px) без вертикального скролла; галереи/архивы — отдельные роуты/панели.

**Acceptance criteria:**
- На ширине ≥1440px главный борд (Сегодня + Календарь + ряд статов + now-playing + индикатор темы) виден без скролла.
- Все цвета/шрифты/радиусы берутся из активной темы (§6), не хардкодятся.

**Technical considerations.** CSS Grid; все визуальные значения — через CSS-переменные (design tokens).

### 5.2. Плитка «Сегодня»
**Описание.** Центральный фокус: крупная дата + **имя дня** + дисциплина дня картой-тропой (включая «монстра»). **Строк статов в плитке нет:** шаги и сон показываются своими виджетами («активность» 5.4 и «сон»), тренировка ждёт нового дома (бэклог §9), экранное время — бэклог.

**Acceptance criteria:**
- По умолчанию — сегодняшний день (MSK).
- При клике на день календаря перерисовывается на выбранную дату.
- **Относительное имя дня.** Над датой — относительное название выбранного дня на русском: точные термины (*сегодня / вчера / позавчера / завтра / послезавтра*) приоритетнее, затем день недели по календарным неделям (эта неделя — *в понедельник*; соседняя — *в прошлый / следующий вторник*), дальше — *N дней назад / через N дней* (с корректным склонением). Отрисовка — по стилю активной волны (DESIGN §4).
- **Выбор дня соседнего месяца** визуально отличим (фон плитки чуть меняется), согласованно с приглушением такого дня в календаре (5.3).
- **Имя дня** (короткий заголовок, напр. «первый забег») показывается в одной строке с датой — дата слева, имя справа (компоновка и типографика — DESIGN §4); задаётся владельцем и редактируется задним числом (см. 5.6). Если имени нет — дата занимает строку одна, элемент имени не рендерится.
- Отсутствующие данные — «нет данных», не 0 и не ошибка (null ≠ 0 — см. 5.4); правило действует в виджетах статов, куда строки шагов/сна переехали из этой плитки.
- **Монстр — только внутри карты-тропы (5.6).** Факт «пил/не пил» читается по детур-остановке «монстр» на карте; **отдельной строки/пометки «монстр: не пил» и картинки банки внизу плитки нет** (дублировала карту). Вкусо-специфика (пиксель-банка, название вкуса) — бэклог: приземлится в саму карту (на детур), не отдельным блоком.

**Technical considerations.** Источник — `GET /api/days/{date}`. «Монстр» в плитке — состояние детура карты-тропы (`monster != null`); сам вкус нигде на борде не показывается (5.3), картинка банки вкуса — бэклог карты.

### 5.3. Календарь-навигатор (окно целыми неделями)
**Описание.** Главное взаимодействие. Окно — **четыре полные недели пн→вс**: две прошлые, текущая и следующая (28 дней). Ховер по дню = мини-превью; клик = перефокус «Сегодня». Прошлые месяцы пока не листаются (бэклог).

**Границы режутся по неделям, а не по «±N дней».** Календарь — сетка недель, и окно, начинавшееся с произвольного дня (было ±15 от сегодня), давало рваный первый ряд: прошлая неделя показывалась наполовину, а слева висели пустые ячейки-заполнители. Целые недели дают ровный прямоугольник 7×4 без заполнителей, и «две недели назад» читается как две недели, а не как «примерно столько же дней». Число недель до/после — параметры окна, а не константа в компоненте.

**Линза дисциплины: календарь как фильтр по одной остановке.** Клик по иконке остановки на карте-тропе в «Сегодня» (5.2, 5.6) включает **линзу** — календарь размечает дни, в которые эта остановка была закрыта. Линза это не режим карты, а **взгляд календаря**: она переживает смену выбранного дня (иначе разглядывать историю пункта было бы нечем) и снимается тремя способами — повторным кликом по той же иконке, крестиком в ярлыке календаря, `Esc`. Крестик обязателен, а не декоративен: в выходной карта-тропа уступает место сцене отдыха (5.6), и кликнуть по остановке повторно становится негде.

**Выбирается остановка, а не пункт.** У пунктов с `target = 2` (чтение, подкасты) остановок на маршруте две, и они несут разные вопросы: «читал хоть раз» и «читал дважды». Порог остановки — `count ≥ occurrence`, ровно тот же, каким считаются её огоньки-стрики (5.6). Поэтому все восемь иконок карты — восемь разных выборок, а не шесть.

**Ответов у линзы три, а не два.** «Совпал» / «не совпал» / **«ответа нет»** — последнее у дня без записи (пропуск, будущий день) и у ответа из устаревшего клиентского кэша. Без третьего состояния дырка в записи читалась бы как «не сделал», то есть отсутствие данных выдавалось бы за факт (та же ошибка, что уже чинили в заливке ячейки).

**Acceptance criteria:**
- Видно окно из четырёх полных недель пн→вс (две прошлые, текущая, следующая) в MSK.
- **Сетка выровнена по дням недели:** неделя начинается с понедельника, новая неделя — новой строкой; выходные (сб/вс) визуально отличимы; дни не текущего месяца приглушены (отрисовка — по стилю активной волны, DESIGN §5).
- Ховер по дню (desktop) = мини-сводка (включая относительное имя дня, см. 5.2) без перехода; **на тач ховера нет — тап сразу выбирает день**, сводку показывает перефокус «Сегодня» (см. 5.10).
- Клик = смена фокусного дня; дни с данными отличимы от пустых.
- **Вкус монстра в календаре не отображается** — ни цветовой меткой в ячейке, ни строкой в ховер-сводке (то же в недельной полосе 5.10). Вкусы продолжают приниматься и храниться (5.6), но остаются данными: факт «монстр выпит» читается только по карте-тропе в «Сегодня» (5.2). Решение владельца, DESIGN §6.

- **Линза:** клик по остановке карты-тропы включает её, повторный клик / крестик в ярлыке / `Esc` — снимают; ярлык календаря называет активную линзу. Совпавшие дни отмечаются в стиле активной волны (DESIGN §5), несовпавшие приглушаются, дни без ответа не меняются. Ответ линзы едет в ховер-сводку и подпись для скринридера; остановки доступны с клавиатуры.
- **Линза монстра инвертирована:** отмечаются дни **без** монстра — как и его огонёк-стрик, который считает «дней чисто» (5.6). На карте детур «пройден», когда монстр выпит, но достижением в календаре является чистый день. Решение владельца. Поэтому и ярлык у неё развёрнутый — «календарь — **не пил монстр**»: одно слово «монстр» не сказало бы, что именно отмечено.
- Недельная полоса на мобиле (5.10) — тот же календарь, размечается линзой так же.

**Technical considerations.** Диапазон одним запросом `GET /api/days?from=&to=`, кэш на клиенте. Сводка дня несёт `disciplineCounts` — счётчик по **каждому активному пункту**, включая нули: свёртки «N из M закрыто» линзе мало (порог остановки — `count ≥ occurrence`), а нули нужны, чтобы «пункт был, не сделан» отличалось от «пункта не существовало». Фильтрация целиком клиентская — данные окна уже в руках у борда, клик по иконке в сеть не ходит. Поле опционально на чтении: ответы старого кэша его не несут и деградируют в «нет ответа», а не в «не сделал».

### 5.4. Apple Health (шаги, сон, тренировки)
**Описание.** Данные из HealthKit заливаются iOS-шорткатом 12:00 / 18:00 / 24:00 MSK. Облачного API у Apple нет — пушит устройство. Два виджета: **«Активность»** (DESIGN §7.4) — динамика **шагов и сна** двумя графиками за период (значение выбранного дня + среднее по окну); **«Сон»** (DESIGN §7.7) — детали ночи выбранного дня (длительность, пробуждения, **фазы сна** барами).

**Частичность данных — норма, не ошибка.** Любая метрика может отсутствовать за любой день и это штатно: тренировка — не каждый день (обычно ~2 раза в неделю), сон не посчитался (часы не надели), шаги нулевые. Поэтому:
- **`0` — валидное значение** (например, 0 шагов), отображается как `0`, не как «нет данных».
- **Отсутствие метрики** (null) — «нет данных», отдельно от нуля. Различать на уровне модели (nullable-поля), не схлопывать в 0.
- **Исключение — сон.** У ночи нет осмысленного «реального нуля»: `sleepMinutes = 0` означает «сна не было» (шорткат шлёт 0, когда за день нет сессии сна в HealthKit). Поэтому при приёме 0-минутная ночь нормализуется в `null` — и длительность, и фазы гасятся (рисовать нечего), плитка показывает пустое состояние, а не «0м» с пустыми барами. Шаги остаются обычным null≠0.
- Архитектурно каждая метрика независима: блок рендерит то, что есть, пустые — тихо опускает/помечает «нет данных».

**Сон считает бэкенд, а не шорткат.** Ночь лежит в HealthKit пачкой кусков-фаз по обе стороны полуночи, а принадлежит она **дню пробуждения** (§4). Любой фильтр шортката по одной границе семпла режет ночь: `Start Date is today` теряет вечернее начало, `End Date is today` — куски, закончившиеся до полуночи (уснул 23:20 ⇒ ночь показывалась «с 00:00»; баг найден 2026-07-28). Поэтому шорткат не считает ничего: он отдаёт **сырые куски за широкое окно**, а день выбирается на бэке — по **концу сессии**. Ширина окна перестаёт быть настройкой: лишнее отбрасывается, недобрать нельзя.
- **Сессия** — куски подряд с разрывом между ними менее часа; в день D попадают все сессии, закончившиеся в D (ночь + дневной сон того же дня).
- **Перекрытия разбираются по времени, а не суммированием.** Время режется границами всех кусков, каждый элементарный отрезок достаётся одной фазе (явная фаза бьёт неразмеченный сон). Отсюда бесплатно: дубли источников не удваивают ночь (Shortcuts не дедуплицирует семплы), разметка часов поверх записи телефона не удлиняет её, `In Bed` в сон не входит.
- **Ночь без часов** — один семпл `Asleep` без фаз: считается как light, длительность честная (раньше уходила нулём — семпл не попадал ни в одну ветку `If`).
- Незнакомое имя фазы пропускается молча (имена задаёт Apple), **битая дата — 400**: это поломка шортката, о ней надо узнать сразу.

**Acceptance criteria:**
- `POST /api/ingest/health` (токен) принимает за дату: `steps`, сон, список `workouts` (каждая — тип, длительность, калории `activeEnergyKcal`, дистанция).
- Сон принимается в двух формах. Основная — `sleepSegments: [{stage, start, end}]`: сырые куски (`stage` — голое имя фазы с iOS: `REM`/`Deep`/`Core`/`Awake`/`Asleep`/`In Bed`; границы — ISO, со смещением либо без него в MSK). Легаси — готовые `sleepMinutes` + опц. `sleepStages {rem, deep, light, awake}` в минутах. Пришли куски — они и побеждают; пустой список кусков = «сна не было».
- Повторный POST за дату — идемпотентный upsert.
- **Пустой прогон не стирает сон.** Пришли куски, но ночи из них не собралось ⇒ поля сна не трогаются (ответ несёт `sleepSkipped: true`), потому что «шорткат не достал» и «не спал» по данным неразличимы, а первое случается заметно чаще. Стереть записанную ночь можно явным `sleepMinutes = 0`. Шагов это не касается — 0 шагов остаётся честным нулём.
- Вечерний прогон фиксирует полный день; пропущенный прогон догоняется следующим (Health отдаёт весь день).
- «Активность» — два линейных графика (шаги + сон) за окно с прокруткой до 30 дней; значение выбранного дня + среднее по видимому окну; ось Y автомасштабируется по окну (с минимальным размахом), маркер стоит на выбранном в календаре дне. Дни без данных — разрывы, не нули.
- **Фазы сна** (если пришли): REM / deep / light / awake в минутах — показываются в виджете «Сон» пиксельными барами с долями. Если фаз нет (часы не носились) — только общая длительность; нет сна за день — пустое состояние (пиксельная кровать).
- **Тренировки** в этих виджетах пока не отображаются (принимаются и хранятся; вывод — бэклог).

**Technical considerations.** Health-шорткат **без ввода** → крутится по time-automation сам. Тело — JSON. Фазы сна доступны из HealthKit с iOS 16 (`HKCategoryValueSleepAnalysis`: `asleepREM/asleepDeep/asleepCore`≈light/`awake`); шорткат перекладывает куски как есть (фаза + две даты), сборкой ночи занимается `SleepSessionizer` на бэке. Извлечение через Shortcuts провалидировано на устройстве — воспроизводимая схема и грабли в **Приложении А.2**; при отсутствии фаз (ночь без часов) фича деградирует до общей длительности. Графики — на данных `GET /api/days?from=&to=` (виджет статов тянет свою выборку последних 30 дней; фазы за выбранный день — из полной проекции `GET /api/days/{date}`), без отдельного эндпоинта.

### 5.5. Spotify (now-playing / недавние / топы)
**Описание.** Живой опрос Spotify Web API. Свою историю в v1 не копим. Музыкальный блок (DESIGN §7.1): когда трек играет — характерный **виджет в стиле нативного Spotify** (обложка, название, исполнитель; прогресс-бар трека — бэклог B8, §12); когда нет — «последний трек играл N назад» либо «ничего не играет», ниже — список недавних треков.

**Acceptance criteria:**
- `GET /api/spotify/now-playing` — текущий трек или пусто (ничего не играет).
- `GET /api/spotify/recent` — **список** последних проигранных треков (Spotify `recently-played`, лимит API 50), у каждого `playedAt` → фронт считает «N минут/часов назад».
- `GET /api/spotify/top?range=short|medium|long` — топы за ~4 нед / 6 мес / всё время (задел; в UI — переключатель «топ за последний месяц», `range=short`).
- now-playing **обновляется при загрузке страницы и далее каждые ~20 секунд** (в такт TTL серверного кэша); **в скрытой вкладке опрос приостанавливается** (`visibilitychange`), при возврате на вкладку — немедленное обновление: забытая открытой вкладка при возврате показывает актуальное, а не застывшее, и не жжёт запросы в фоне.
- **Список недавних не двоит подряд идущие одинаковые треки** — повтор трека, сыгранный сразу за собой же, показывается одной строкой (повторы «через один» остаются: это отдельные прослушивания).
- **Виджет сжимается по ширине под объём описания** (визуал — DESIGN §7.1): узкий трек ⇒ компактная центрированная карточка, широкий ⇒ полная ширина; перегон плавный и живой (пере-сжимается при смене трека в фоне).
- **Когда трек играет:** виджет визуально считывается как «вырезанный из приложения Spotify» (дефолт). Волна может переопределять оформление виджета, но дефолт — спотифаеподобный.
- **Когда ничего не играет:** показываем «последний трек играл N назад» (из `recently-played.playedAt`); если и недавнего нет — «ничего не играет».
- Переключатель на **«самый сок за последний месяц»** (топ-треки `range=short`) — подписан честно, без выдачи топа за «сейчас».
- На блоке Spotify — корректная атрибуция (лого/ссылка) по dev-условиям.

**Technical considerations.** OAuth Authorization Code; **refresh-токен шифруется at-rest**. **quarkus-cache (Caffeine):** now-playing TTL ~20с, recent/top — минуты → один upstream-вызов на всех посетителей, лимиты Spotify не превышаются. «Последний трек игрался N назад» берётся прямо из `recently-played` (`playedAt`), **своя история не нужна**; серверный кэш — лишь защита от лимитов API, а не источник истории. Ограничение: recently-played — только 50, посуточной истории нет. 20-секундный фронт-поллинг разделяет тот же серверный кэш (TTL ~20с) → upstream не растёт; в скрытой вкладке поллинг стоит.

### 5.6. Дисциплина (расширяемый чеклист) + «монстр»
**Описание.** Блок называется **«Дисциплина»**. Ежедневные пункты, расширяемые без релиза. Пункт **не бинарный**, а имеет **цель-количество** (`target`): растяжка = 1 раз (по сути да/нет), чтение = 2 раза/день, подкасты = 2/день. На фронте чеклист визуализируется **картой-маршрутом дня** «утро → ночь» (пункты — остановки тропы; отрисовка — по стилю активной волны, DESIGN §4.1), в хранении — одно число прогресса в одной записи за дату+пункт. Плюс **«монстр»**: за день — конкретный вкус энергетика (банка с картинкой) либо «не пил»; картинка/цвет дают дню акцент.

**Состав первой итерации (сид пунктов):**
1. **Растяжка** (цель 1)
2. **Чтение** — 2 раза по 30 мин (цель 2)
3. **Английские подкасты** — 2 шт (цель 2)
4. **Дневник перед сном** (цель 1)
5. **Офис по расписанию** (цель 1)
6. **Монстр** (цель 1) — пункт «пил/не пил»; **связан** с выбором вкуса (см. ниже)

**Монстр = и пункт дисциплины, и сущность вкуса (решение).** Пункт «монстр» в списке отражает факт «пил/не пил»; параллельно сохраняется **конкретный вкус** (`MonsterFlavor`) для пиксель-банки в «Сегодня» и акцента в календаре. Отметка пункта и выбор вкуса согласованы: выбран вкус ⇒ пункт «выполнен»; «не пил» ⇒ пункт не выполнен и вкуса нет.

**Дневник ставится временем, а не галочкой (второй производный пункт).** Приложение «Журнал» умеет писать проведённое в нём время в HealthKit как **Mindful Minutes** (Настройки → Приложения → Журнал → Health Access → Mindful Minutes). Значит пункт «дневник перед сном» можно не отмечать вручную — он выводится из данных, как «монстр» выводится из вкуса. Правило: **≥ 15 минут** в вечернем окне **`[D 19:00, D+1 02:00)`** MSK ⇒ пункт выполнен за день D. Все три числа — конфиг (`danchuo.journal.window-start/window-end/min-minutes`), потому что это привычка владельца, а не константа.

Почему окно, а не календарные сутки: день владельца идёт с 7 утра до 2–3 ночи, дневник пишется перед сном — часто уже после полуночи. По календарным суткам один вечер делился бы надвое, и обе половины не добирали бы порог. Почему обрезка по краям окна: «Журнал» открывают и днём (в живых данных — россыпь кусков в 13:00–16:00), дневное сидение не должно вытягивать вечернюю отметку.

Три контрактных решения, каждое — прямое следствие уже пройденных граблей:
- **Куски считает бэк**, шорткат тащит сырьё за широкое окно (34 часа = две вечерние корзины). Один прогон закрывает и вчерашний день — иначе полуночный прогон терял бы хвост после полуночи навсегда (дата запроса на раскладку не влияет, §4).
- **Производный канал пишет только «сделано»**, нуля — никогда. Ноль занял бы слот и заблокировал более поздний прогон того же вечера; «мало минут» и «шорткат не достал» по данным неразличимы — та же логика, по которой пустой прогон не стирает ночь (§5.4).
- **Ручная галочка перекрывает минуты.** Пункт `journal` в `items` продолжает приниматься и пишется поверх всегда, производный канал занимает только пустой слот. Это аварийный ход (писал на бумаге, отозван доступ Health), а не штатный путь: штатно `journal` в `items` не шлётся вовсе. Обратная сторона решения — сняв галочку руками, вернуть день под автоматику уже нельзя.

**Acceptance criteria:**
- Пункты (с `target`) и вкусы задаются данными (новый добавляется без деплоя).
- `POST /api/ingest/daily` (токен) за дату: прогресс пунктов (`{itemKey: count}`), `monsterFlavorKey: string|null`, **`title: string|null`** (имя дня), (позже) `screenTimeMinutes`, `readingProgressPercent`.
- Прогресс пункта хранится одним числом (`0..target`); фронт рендерит «`count/target`».
- **Имя дня** вводится тем же интерактивным iOS-шорткатом (Ask for Input → текст) и редактируется задним числом повторным ingest за дату (идемпотентный upsert).
- **Семантика повторной отправки за тот же день:** присланные пункты перезаписываются (не суммируются); **не** присланные в `items` пункты сохраняют прежние значения; `title` и вкус монстра — снапшот последней отправки (пустой `title` очищает имя, пустой/отсутствующий `monsterFlavorKey` сбрасывает в «не пил»).
- **Окно ручного ввода:** дата принимается только в диапазоне **[сегодня − 31, сегодня] по MSK** (конфиг `danchuo.checklist.ingest-window-days`); будущее и глубже окна ⇒ 400 `date_out_of_window` — защита от опечатки в дате на телефоне.
- **Измеренные минуты видны на карте-тропе.** Сумма за вечернее окно сохраняется в `DayRecord.journalMinutes` и приезжает в проекции дня как `DisciplineItemView.measuredMinutes` — под остановкой «дневник» пишется «23 мин» (визуал — DESIGN §4.1). **Минуты пишутся и ниже порога** (это главный их смысл: «6 мин» под незакрытой остановкой отвечает на вопрос «почему не засчиталось», не заглядывая в логи) **и независимо от того, кто поставил отметку** — измерение и решение разные вещи, ручной приоритет касается только решения. `null` = «не мерили» ⇒ строка не рисуется: у ручной отметки и у всех дней до появления канала цифры не будет, пока день не перешлют.
- **Дневник — производный пункт.** `POST /api/ingest/health` принимает `mindfulSegments: [{start, end}]` (сырые куски, ISO со смещением или без — тогда MSK). Битая дата ⇒ 400 `mindfulSegments[i].start|end` (поломка шортката, о ней надо узнать сразу). Минуты раскладываются по вечерним корзинам **независимо от `date` запроса**; день с суммой ≥ порога получает отметку, но **только если отметки за (день, `journal`) ещё нет**. Ответ несёт диагностику `journalMinutes: {день: минуты}` и `journalDays: [дни]` — её читают глазами в `Show Result` на телефоне, поэтому по ответу различимы «не добрал порог» (минуты есть, дня в `journalDays` нет) и «решено вручную» (то же самое, но отметка в базе уже стоит).
- В «Сегодня» — **карта-маршрут дисциплины**: пункты — остановки тропы «утро → ночь»; пункт с целью 2 даёт **две** остановки в разных местах дня; «монстр» — тупиковое ответвление-детур (не на основном маршруте — необязателен для идеального дня). Состояние остановки выводится из счётчиков (времени выполнения в модели нет): сделана / **пропущена** (не сделана, а более поздняя уже закрыта — день ушёл дальше) / ещё впереди; все остановки закрыты ⇒ маршрут подсвечивается целиком. **Итоговой дроби «N/7» на карте нет** — прогресс читается остановками, а цифра поверх картинки работала как оценка за день; для скринридера счёт остался в описании карты. Плюс банка вкуса + имя дня; в превью календаря — акцент монстра и маркер «есть имя» (отрисовка — по стилю активной волны, DESIGN §4.1). **На выходных (сб/вс MSK) карта уступает место сцене отдыха** — все дела будничные, а пустая тропа в выходной читалась бы как провал; монстр остаётся единственным перенесённым элементом (визуал — DESIGN §4.2).
- **Стрики дисциплины.** У каждой остановки — текущая непрерывная серия дней: сколько дней подряд пункт **выполняется**; у монстра — инверсия «сколько дней подряд **не** пью». Правила: (1) **отсчёт «по вчера, тикает вечером»** — сегодня входит в серию только если уже заполнено и выполнено, иначе серия считается по вчерашний день; незаполненное/невыполненное сегодня серию **не роняет** (обнулится лишь назавтра); (2) **разрыв строгий** — день без записи ИЛИ с невыполненным пунктом обрывает серию (правка задним числом пересчитывает автоматически); (3) серия считается **по каждой остановке** отдельно (у двойного пункта «дней с ≥2» ≤ «дней с ≥1»); (4) монстр «чист» в день, только если запись за день есть и вкус не выбран; (5) **выходные (сб/вс MSK) для дисциплины нейтральны** — все дела будничные, поэтому выходной **не входит** в серию (не учитывается) и **не обрывает** её (не сбивает): серия «перешагивает» уик-энд и продолжается в понедельник с пятницы. Монстр — **исключение**: его серия «чисто» считается **каждый** день, включая выходные. Стрик приходит в проекции дня (`DisciplineItemView.occurrenceStreaks`, `DayView.monsterCleanStreak`); на борде показывается от 2 (отрисовка — DESIGN §4.1).

**Technical considerations.** Стрик считается **на бэке** сканом истории назад от просматриваемого дня до первого разрыва (см. `StreakCalculator`); чтобы скан не повторялся на каждую перезагрузку, проекция дня **кэшируется** (`day-view`, ключ `(date, today)` — сам протухает в полночь MSK) и **сбрасывается из единой точки записи** (`DayRecordService`, оба канала ingest), а история читается **батчами** назад (лениво, до первого разрыва).  Ввод — **интерактивный iOS-шорткат** (реализованная схема — Приложение А): имя дня → мультивыбор сделанных пунктов → мультивыбор вкуса (пусто = «не пил») → выбор даты (обычно сегодня; окно −31 день) → POST. С домашнего экрана/кнопки действия, опц. напоминание-автоматизация. v1 — один вкус на день (мультивыбор = тривиальный many-to-many). Вкусы и пункты сидятся статикой/API (новый вкус = INSERT, как ultra-white). Установка пункта «монстр» — производная от выбора вкуса (не отдельный ручной ввод).

### 5.7. Проекты (компактный выпадающий блок)
**Описание.** Проекты с привязкой к **временно́му промежутку** в небольшом раскрывающемся блоке. Каждый проект: маленькая иконка-картинка, название, диапазон дат вида «квартал года — квартал года», опциональная ссылка (GitHub и т.п.) **гиперссылкой на названии**.

**Acceptance criteria:**
- `GET /api/projects` — идущие «по настоящее» проекты сверху, завершённые ниже; внутри групп — по дате начала промежутка (новые сверху), при равенстве — `sortOrder`.
- Поля: **иконка** (`iconUrl`), **название**, **начало** (год + квартал), **конец** (год + квартал, опц. — пусто = «по настоящее»), **ссылка** (опц.).
- Диапазон отображается как «Q3 2025 — Q1 2026» (или «Q3 2025 — наст.»); совпадающие края (проект, живший один квартал/год) схлопываются в единственный край — «Q2 2026».
- Название кликабельно ⇔ задана ссылка; без ссылки — просто текст (не «мёртвая» ссылка).
- **Список листается без видимого ползунка** — колесом мыши, трекпадом и тачем; подсказка о продолжении — обрезанный краем элемент, как у полки фото-дропов (5.12). Перетаскивания мышью нет намеренно: оно перехватывает клик по проекту.
- **Спрайт, название, диапазон и зазоры — доля своей плитки, а не пиксельные константы** (DESIGN §8.1). Оптическая компенсация «гладкий флэт на ступень крупнее пиксель-арта» сохранена как соотношение долей.

**Technical considerations.** В v1 наполняется сид-конфигом / прямым API. Иконки — спрайты-«планетки» проектов, wave-agnostic статика фронта `/assets/projects/` (один спрайт на все волны; слот 28px у пиксель-арта / 32px у гладких — оптическая компенсация; конвенция имён и рендер — DESIGN §12.2); сторонние фавиконы-URL рендерятся легаси-мелко (20px, скругление).

### 5.8. Соцссылки + избранное фото + marquee артефактов
**Описание.** Блок соцссылок (иконка + название + гиперссылка); один hero-снимок; **бегущая строка артефактов** — курируемый набор реальных предметов (демо-заглушки сняты; сейчас — Cyber Y2K Sunglasses, ракетка YONEX ASTROX 10 WHITE PINK 4U, плёночная мыльница Pentax Espio 738). Артефакт несёт картинку или GIF и **дату первого упоминания**; на ховер — всплывающее окно с увеличенной картинкой, под ней название и (мельче) дата первого упоминания.

**Acceptance criteria:**
- `GET /api/social-links` — ссылки с **иконкой, названием** и порядком; каждая — гиперссылка. Виджет — **сетка карточек** (все ссылки видны разом; в узкой плитке подписи прячутся, остаются иконки, имя — в `aria-label`); бегущая строка соцссылок снята (DESIGN §3). Рендер иконки — деталь **скина** активной волны: базово — одноцветный спрайт, крашенный токеном через CSS-маску; волна может нести собственные цветные спрайты (статика фронта, DESIGN §3). Плашка-подложка карточки-ссылки — тоже параметр скина: базово приглушённая, волна может её погасить (карточка-тач-таргет остаётся).
- **Иконка, подпись и зазоры — доля своей карточки, а не пиксельные константы** (DESIGN §8.1): на большом мониторе иконки иначе разъезжаются и тонут в карточках, на маленьком — давятся. Плитка соцсетей — пилот этого подхода на весь борд.
- `GET /api/artifacts` — артефакты: `id`, название, картинка/GIF (`imageUrl`), **дата первого упоминания** (`firstMentionedOn`), разрешение класться набок (`rotatable`), порядок. `id` нужен, чтобы соотнести предмет с рамкой его подсветки на кадре дропа (§5.12).
- **Артефакты заводятся из `/admin`, а не миграцией.** Раньше каждый новый предмет означал правку кода и раскатку. Форма несёт все поля: название, картинка (загрузка файлом), дата первого упоминания, «можно класть набок», порядок в ленте и **описание для поиска на кадрах** (`detectionHint`, §5.12). Картинка одна на все волны. Эндпоинты — `GET|POST /api/ingest/artifacts`, `PUT|DELETE /api/ingest/artifacts/{id}`, `POST …/{id}/image`; раздача — `GET /api/artifact-media/{id}` (кэш час, а не месяц: картинку предмета можно переснять, оставив тот же id).
- **Описание для поиска можно попросить у модели** — `POST /api/ingest/artifacts/{id}/hint` показывает ей загруженную картинку и просит одну английскую фразу («a white and pink badminton racket»). Формулировка напрямую влияет на качество поиска, а сочинять её вручную муторно. Задачу намеренно решает **дешёвый провайдер** (`GroqLlmClient` инъектируется в сервис напрямую, минуя выбор `danchuo.llm.provider`): описать картинку словами умеет любая vision-модель, платить за это координатной незачем. Модель молчит ⇒ `hint: null` и поле остаётся за человеком — это штатный ответ, а не ошибка.
- Картинки, заведённые через админку, лежат в хранилище (`danchuo.artifacts.storage-dir` — подкаталог тома фото-дропов, чтобы не заводить в проде второй), засеянные миграциями остаются статикой фронта: `imageUrl` — просто URL, оба источника уживаются.
- Hero-снимок — **временно снят с борда** (тайл в реестре, `hidden` в дефолт-раскладке; вернётся отдельной перекомпоновкой/волной). Лента прокручивается **только когда предметов больше, чем влезает в тайл** (иначе они стоят статично по центру — единственный предмет не двоится); уважает `prefers-reduced-motion`.
- Предмет в ленте **весит столько же, сколько соседи** (равная площадь, а не равная высота) и **может лечь вдоль ленты, если ему это разрешено** (`rotatable` у артефакта, по умолчанию нет — вещь показывается как нарисована; хранится разрешение, а не ориентация: куда поворачивать, считается по пропорции картинки). DESIGN §7.2.
- **Клик по артефакту** → небольшое **меню-модалка по центру экрана** (затемнённый фон, закрытие по `Esc`/клику по фону): увеличенная картинка/GIF + название + мельче дата первого упоминания. В самой ленте дата не показывается — только в меню (DESIGN §7.2).

**Technical considerations.** Артефакты — фиксированный набор (статика/ассеты), поддержка GIF. Дата первого упоминания хранится всегда, в UI выводится только в поповере. **Новый артефакт = строка в БД (миграция) + PNG в статике фронта `/assets/artifacts/`** — релиза кода не требует. **Порядок ленты курируемый (`sortOrder`), а не хронологический:** предмет с более старой датой первого упоминания не переезжает влево — дата это свойство предмета, а не его место в строке. Картинку рисует владелец, вырезка фона — детерминированный шаг (`experiments/artifact-pixelizer/artifactify.py`: флуд-филл от краёв сквозь фон и мягкую тень, жёсткая альфа, самая большая связная компонента, кроп по предмету). 3D-конвертация — бэклог.

### 5.9. Система тем («волна») + переключатель

> **Что такое «волна» (три слоя).** Волна — это **полностью самостоятельный визуальный мир**, а не палитра. Чтобы будущие волны могли быть *совершенно непохожими* (а не «той же сеткой в других цветах»), волна несёт **три независимых слоя**:
> 1. **Токены** — значения дизайн-переменных (цвет, радиусы, тени; шрифты в токенах не живут — их подставляет `next/font`, а шрифтовые решения волны — слой скина). Меняют то, что уже параметризовано. **Одними токенами принципиально другой стиль не получить** — они не меняют форму элементов.
> 2. **Раскладка (layout)** — композиция плиток борда (переставить/ресайзить/спрятать; §10.1).
> 3. **Скин (skin)** — CSS-слой, переопределяющий то, что НЕ выражается токеном: **форму карточек (рамки/углы), фон, декоративный слой, шрифт меток, анимации**. Технически — ключ волны висит атрибутом `data-wave="<key>"` на `<html>`, а в стилях под него лежат блоки `[data-wave="<key>"]{…}` (DESIGN §10.2). Волна без своего скин-блока берёт базовый скин (= волна 01).
>
> Пример контраста, достижимого только скином: волна 01 — ступенчатая пиксель-рамка на персиковом зерне; волна 02 «Obscura» — мягкие скруглённые «облачные» карты на небе с дрейфующими пиксель-облаками и пиксель-шрифтом меток. Цветами такое не выразить.

**Описание.** Стиль волны (все три слоя выше) сменяем по релизам. В v1 — волна 01 (DESIGN.md) активна, волна 02 «Obscura» — выпущена и доступна переключателем. **Переключатель волн**: ряд **чипов-мини-плиток** — каждый чип нарисован краем и палитрой своей волны, а её сигнальный цвет несёт нижний торец карточки; то есть чип показывает волну формой и палитрой, а не одним цветом страницы (визуал — DESIGN §2.6). Клик меняет стиль полностью. Направление ряда — капабилити раскладки (`orientation`, как у ленты дропов и проектов); ряд не переносится по ширине, поэтому зум не может самовольно поставить чипы в столбец.

**Acceptance criteria:**
- Все визуальные значения — design tokens (CSS-переменные); ни одного хардкод-цвета/размера в компонентах.
- `GET /api/theme/active` отдаёт токены **и (опционально) раскладку** активной волны (default); ровно одна активна.
- Смена активной волны меняет вид всего сайта (**визуал, скин и композицию плиток**) без правок компонентов.
- Волна может **переставлять, ресайзить, прятать и разворачивать** плитки (опциональный layout-блок; `orientation: horizontal|vertical` — для тайлов с двумя режимами потока контента: лента артефактов, полка фото-дропов, список проектов); не задано ⇒ дефолтная раскладка (DESIGN §3, §10.1).
- Волна может нести **собственный скин** (`[data-wave]`-CSS): своя форма карточек/фон/декор/шрифт, не только цвета (DESIGN §10.2). Базовый скин (волна 01) при этом не затрагивается.
- Переключатель: **только свотчи реально выпущенных волн** — по одному на волну, **без слотов-заглушек** под будущие (пустые квадраты читались как недоделанный UI). Новая волна появляется в ряду фактом релиза. Клик → клиентский своп токенов в `:root`, **переключение `data-wave`** и раскладки борда — без перезагрузки.
- **Выбор посетителя персистентен:** выбранная волна запоминается (cookie `danchuo_wave`, срок — год) и переживает перезагрузку/повторный визит — SSR рендерит сразу её, без вспышки волны владельца. Неизвестный/устаревший ключ в cookie тихо игнорируется (фолбэк на активную волну). Явный выбор посетителя приоритетнее смены активной волны владельцем.
- Переключатель — **компактный** (небольшой блок в верхнем ряду, DESIGN §3); не доминирует на экране.

**Technical considerations.** Токены **и layout-блок** — в БД (JSONB); фронт инжектит токены в `:root`, раскладку — в борд, ключ волны — в `data-wave` на `<html>` (SSR + клиентский своп, без вспышки). **Скин** живёт в CSS фронта (`globals.css`, блоки `[data-wave="<key>"]`), не в БД: это код визуала, ревьюится как код. Реестр плиток — за кодом фронта; волна раскладывает существующие плитки (мерж дельты поверх дефолта). Переключение — клиентское среди выпущенных волн (`GET /api/themes`); канон «active» задаёт владелец. Персистентность выбора — cookie (`waveCookie.ts`): клик пишет ключ, SSR читает его и резолвит волну через `GET /api/themes` (`fetchDisplayTheme`, фолбэк — `GET /api/theme/active`). SSR-фетчи тем идут через Next data cache (ревалидация ~30с): шторм перезагрузок не выедает рейтлимит бэкенда (иначе SSR деградировал в дефолт — без `data-wave` и обводки свотча). Если SSR всё же деградировал (бэк лежал), переключатель самовосстанавливается на клиенте: получив список волн, применяет волну из cookie (или активную) без перезаписи cookie. Открытый вопрос (DESIGN.md §2.6): доступно всем vs только превью — по умолчанию для всех.

### 5.10. Адаптивность и масштабируемость
**Описание.** Достойно на любом размере — от 27" до телефона, без зум-ужаса. Bento осознанно перестраивается, а не сжимается 1-в-1.

**Acceptance criteria:**
- **Режим борда определяется типом указателя, а не шириной окна.** Мышь/трекпад ⇒ полный bento; грубый указатель (палец) ⇒ мобильный стек при любой ширине, включая планшет в альбомной. Причина: браузерный зум ужимает CSS-вьюпорт, и порог по ширине ронял десктопный борд в телефонный стек с одного шага зума. **Порога по ширине нет вовсе** — десктоп остаётся десктопом, как ведут себя крупные сайты. Реализация/замеры — DESIGN §8.
- **Desktop (мышь):** полный bento без скролла **при любом зуме и любой ширине окна**.
- **Tablet:** тач-планшет — стек при любой ширине.
- **Содержимое плиток пропорционально своей плитке, а не задано в пикселях** (доля контейнера с демпфером роста 50% — на большом мониторе контент растёт, но вдвое медленнее ширины: монитор смотрят с того же расстояния, что и ноутбук, и линейный рост раздувал бы борд; DESIGN §8.1) — иначе на большом мониторе начинка виджета разъезжается и тонет, а на маленьком давится. Переведён весь борд, включая модалки-оверлеи (они ведутся от экрана, а не от плитки — контейнер у них и есть вьюпорт). Исключения осознанные: мета-подписи плиток масштабируются от экрана (образуют общий ряд по борду) и пины карты остаются фиксированными — их спрайты упрощены именно под ~34px, крупной карте нужна подмена ассета, а не масштаб. Подробности и замеры — DESIGN §8.1.
- **Mobile <640px:** одноколоночный стек (Сегодня → календарь → статы → now-playing → … → marquee → **переключатель волн** → свежесть; точный порядок — `MOBILE_ORDER`/`mobileOrder` волны), без горизонтального скролла страницы. **Переключатель волн присутствует и на мобиле** — полноценной плиткой в конце стека, волны переключаемы с телефона.
- **Календарь на тач:** ховер-превью заменяется тапом — тап выбирает день и перефокусирует «Сегодня» (она и есть сводка выбранного дня); на мобиле допустима недельная полоса. **Полоса при открытии автопрокручена к текущей дате** — «сегодня» стоит по центру видимой области (окно ±15 дней; долистывать до сегодня вручную не нужно).
- Тач-таргеты ≥44px; флюидные шрифты (`clamp()`); `prefers-reduced-motion`; адаптивные картинки (`next/image`).

**Technical considerations.** Mobile-first на Tailwind-брейкпоинтах. Hover-зависимый календарь обязательно с тач-эквивалентом с самого начала.

### 5.11. Аналитика посещений (минимальная, приватная)
**Описание.** Свой счётчик в Postgres: заходы в день, уники, время на странице. Без третьих сторон, cookieless. В v1 статистика приватная (только владелец).

**Acceptance criteria:**
- На публичных страницах — **JS-бикон**: POST при загрузке + добивка на `visibilitychange`/выгрузке (даёт время на странице).
- Уники считаются **суточным хэшем** `sha256(ip+ua+соль+дата)` (соль — статический серверный секрет; дата в составе хэша даёт ежесуточную ротацию — назавтра посетитель неузнаваем), **сырой IP не хранится**.
- Боты фильтруются: бикон (краулеры без JS не считаются) + блоклист User-Agent + игнор без `Accept-Language`/HEAD.
- Приватная вьюха владельца: заходы/день, уники/день, среднее время. Куки не ставятся.
- Сырые события хранятся (трафик мал); агрегация — позже.

**Technical considerations.** Сущность `AnalyticsEvent` (§7). Referrer пишется в сырьё сразу, но **в UI выводится позже** (бэклог). Публичный счётчик («посетитель №N») — бэклог.

#### Хитмапа кликов (B2)
**Описание.** «Иногда посматривать», куда реально кликают/смотрят на борде — своё cookieless-решение, без третьих сторон (Clarity/GA сознательно не берём: ставят cookie, пишут сессии вовне, требуют consent-баннер — против приватного контура §11). Модель **потайловая, а не пиксельная**: адаптивный bento (§3) и смена волн делают сырые экранные координаты бессмысленными, поэтому фиксируем, *по какому тайлу* кликнули, а координаты — как долю (0..1) **внутри** этого тайла (стабильно через вьюпорты/волны; позже из долей можно дорисовать пиксель-облачко внутри плитки).

**Acceptance criteria:**
- **Сбор (`POST /api/analytics/interactions`, публичный, без токена):** бикон копит клики по `[data-tile-id]` и шлёт их **батчем на уходе** (`navigator.sendBeacon`), не по событию. Cookieless, тот же суточный хэш и фильтр ботов, что у бикона; сырой IP не хранится.
- **Анти-накрутка (эшелонирование, §11):** публичный POST нельзя «подписать» (любой клиентский секрет уезжает в браузер) — поэтому не блок, а снижение цены/шума: рейтлимит на IP (тот же `RateLimitFilter`) + жёсткая валидация на записи (потолок батча, длина `tileId`, координаты в [0,1]; брак отбрасывается поэлементно) + **cap-вклада-на-чтении** (один посетитель добавляет в тайл не больше N кликов в агрегате). Данные совещательные — устойчивая агрегация важнее, чем недостижимая «защита от подделки».
- **Просмотр (`GET /api/ingest/analytics/heatmap`, за bearer):** секция хитмапы внизу единого экрана `/admin` (noindex, страница скроллится) рисует bento борда, заливая тайлы интенсивностью кликов + таблица по убыванию. По умолчанию — **последние 7 дней**; `path`/период остаются параметрами API (forward-compat), но в UI не вынесены — публичная страница одна (`/`), за бóльшим окном смотрим в БД. Клики самого владельца не считаются: бикон не трекает `/admin*`.

**Technical considerations.** Сущность `InteractionEvent` (сестра `AnalyticsEvent`, §7): `tileId`, доли `offsetX/YPct`, `viewportW`, суточный хэш, `isBot`. Лежит в слайсе `analytics` (ядро не трогаем). Скролл-глубина и пиксель-облачко внутри тайла — возможное расширение, не v1 фичи.

### 5.12. Фото-дропы (плёночная галерея)
**Описание.** Фото выкладываются **дропами**: пачка (порядка ~36 кадров) за один день — как альбом/событие. Дроп виден в двух местах: (1) **тайл фото-дропов** на борде — последний дроп (несколько уменьшенных фото + подпись «месяц + название альбома») и слева мельче — список прошлых дропов; (2) **модалка-галерея** на весь набор кадров.

> **Статус.** Реализовано (B1). Загрузка кадров — через `/admin` (zip за один дроп: ~36 файлов нельзя залить iOS-шорткатом). Хранилище кадров — за интерфейсом `PhotoStorage`: сейчас **локальный диск** (раздаётся бэкендом), позже подменяется на **объектный сторадж (S3/R2-совместимый)** без правок слайса (§3, §8). До первой загрузки тайл живёт в пустом состоянии. Поверх — **выправление поворота кадров (B9)**: плёночные сканы приходят без EXIF и все горизонтальные, вертикальные/перевёрнутые выправляет vision-LLM (ниже) либо ручная стрелка в `/admin`.

**Acceptance criteria:**
- **Загрузка (`POST /api/ingest/drops`, за bearer):** multipart — `zip` (кадры) + `title` + `date`. Бэкенд распаковывает, **ресайзит каждый кадр в два варианта** (web — для модалки/борда, thumb — для сетки/превью) с учётом **EXIF-ориентации**, кладёт в `PhotoStorage`, пишет строки `FilmDrop`/`FilmPhoto`. Непригодные файлы (HEIC/битые/не-картинки) пропускаются; ответ сообщает `processed`/`skipped`. Месяц-подпись выводится из даты.
- **Обложка («самый показательный» кадр):** `PUT /api/ingest/drops/{id}/cover` помечает один кадр обложкой; по умолчанию — первый. Обложка — то, чем дроп представлен в ленте дропов. Выбор — кликом в `/admin`. Удаление дропа — `DELETE /api/ingest/drops/{id}` (кадры + файлы); удаление одного неудачного кадра — `DELETE /api/ingest/drops/{id}/photos/{photoId}` (кнопка ✕ на кадре в `/admin`; возврата нет — оригиналов не храним, при промахе владелец перезаливает дроп; если удалили обложку, ей становится первый оставшийся; `sortOrder` не пересчитывается — дырки безвредны; заблокировано во время прогона проверки поворота — 409).
- `GET /api/drops` — список дропов: название, дата, месяц-подпись, **thumb-обложка**, количество кадров. `GET /api/drops/{id}` — кадры дропа (web+thumb URL + размеры для композиции, порядок). `GET /api/film-media/{dropId}/{seq}/{variant}` — раздача кадра (публично; локальный режим).
- **Тайлы фото-дропов (два):** крупный «последний дроп» — несколько **случайных** кадров (перетасовка на каждом обновлении) + подпись (месяц + название); и компактная «лента дропов» — список всех дропов с обложками. Клик по любому дропу → модалка. Отдельной страницы-архива нет: сама лента и есть архив.
- **Модалка-галерея:** большое **всплывающее окно** (не новая вкладка), закрывается (× / `Esc` / клик по фону), **скроллится** (≈36 кадров длиннее экрана).
- **Загрузка кадров прогрессивная (blur-up):** кадр не «доливается по чуть-чуть», а сразу стоит из размытого превью и по готовности проступает полноразмерный (лениво — только видимое). Ощущение «наводки на резкость», без пустых прямоугольников и мелькания фона. Визуальные детали — DESIGN §7.5.
- **Компактная лента дропов** (полка) листается вбок колесом мыши / свайпом; клик по дропу всегда открывает его на весь экран.
- **Композиция кадров:** кадры разной ориентации (портрет/ландшафт) **умно компонуются программно** в плотную раскладку «встык по швам» (justified/masonry), минимальные зазоры; базовое соотношение кадра ~3:2 (10:6.7). Не фиксированная сетка — пакуется по реальным размерам. В тайле «последний дроп» вся выборка **никогда не встаёт одной строкой** — ряд ограничен 4 кадрами (полоса из 5 подряд читается некрасиво; детали — DESIGN §7.5).
- **Выправление поворота (B9, §9 п.13):** после загрузки дроп автоматически уходит на **фоновую LLM-проверку поворота** каждого кадра (конфиг-флаг; аплоад не ждёт); бэкфилл старых дропов и повтор — кнопкой в `/admin` (`POST /api/ingest/drops/{id}/orientation`, статус поллится `GET` тем же путём). Направлению поворота модель не доверяем (путает CW/CCW) — она работает **бинарным верификатором**: повороты генерируются локально, модель отвечает «стоит ли фото правильно» про каждый из 4, при неоднозначности — тай-брейк «перевёрнуто ли». Консервативно: гейт «текущее положение YES ⇒ не трогаем» (правильные кадры и пустышки нетронуты), неоднозначные кадры помечаются `ambiguous` и ждут ручной стрелки. Ручной поворот — `POST /api/ingest/drops/{id}/photos/{photoId}/rotate` (90° за клик, кнопка ↻ в углу кадра в `/admin`, не пересекается с кликом-обложкой). Повёрнутые кадры получают `?v=`-версию в URL (cache-bust: `/api/film-media` кэшируется как неизменяемый), у четвертьоборотов width/height в БД меняются местами — justified-композиция честна.

**Technical considerations.** Сущности `FilmDrop` / `FilmPhoto` (§7). У `FilmPhoto` хранятся `width/height` web-варианта — нужны клиенту для justified-композиции без догадок. Байты кадров лежат в `PhotoStorage` под ключом `"{dropId}/{sortOrder}"`; URL-ы вариантов генерятся из ключа, поэтому путь в БД не хранится. Обработка (распаковка, EXIF-поворот, ресайз) — слайс `film` (JDK ImageIO + metadata-extractor). Загрузка zip — крупное тело (лимит `quarkus.http.limits.max-body-size` поднят); раздача кадров исключена из рейтлимита (одна галерея = ~36 GET). В проде каталог — смонтированный том; CDN/Caddy перед стораджем — по необходимости.
Поворот (B9): `OrientationDecider` (алгоритм-верификатор поверх `LlmClient.completeVision`, промты — ресурсы `prompts/*`, дословно с замеров) + `FilmOrientationService` (фоновые прогоны в один воркер с троттлингом `danchuo.film.orientation.throttle-ms` — щадим рейт-лимит Groq free-tier; применение — поворот сохранённых web+thumb, оригиналов нет). На `FilmPhoto`: `orientationCheckedAt` (проверен; повтор не трогает), `orientationApplied` (`none`/`cw90`/`ccw90`/`r180`/`ambiguous`/`manual`), `rotatedAt` (байты перезаписаны ⇒ `?v=`-версия URL). LLM молчит (нет ключа/ошибка) ⇒ кадр остаётся непроверенным и подхватится следующим прогоном.

- **Подсветка артефактов на кадрах.** Предметы из каталога артефактов (§5.8) ищутся на кадрах дропа vision-моделью и подсвечиваются полупрозрачным прямоугольником. **Замерено на живых кадрах прода** (артефакт-страница «Поиск артефактов на фото-дропах»): узнавание предмета работает — своя футболка найдена на всех планах, а чужие белые футболки, футболка с другим принтом, чёрная футболка с красным принтом, белая рубашка поверх красного топа и ч/б кадр отвергнуты; **координаты же зависят от провайдера**: у Groq/qwen рамка систематически уезжает выше цели (второй проход зумом это не лечит — смещение задаётся относительно поданного изображения и воспроизводится на каждом увеличении), у Gemini ложится по месту. Отсюда требование к развёртыванию: подсветка включается **только с провайдером, отдающим координаты структурно** (§9, врез про LLM-инфраструктуру).
  - **Форма рамки — прямоугольник, не полигон** (решение владельца): одна фигура и от модели, и от руки ⇒ одно поле, один рендер, один пересчёт при повороте кадра. Требование к точности намеренно ослаблено до «область рядом с предметом», а не «обводка по контуру».
  - **Координаты — доли кадра (0..1)**, никогда не пиксели: мозаика последнего дропа масштабирует кадры произвольно, thumb и web разного размера.
  - **Что искать, задаёт не имя, а описание.** У артефакта поле `detectionHint` — как предмет выглядит («бело-розовая бадминтонная ракетка»): каталожное имя (`YONEX ASTROX 10 WHITE PINK 4U`) для поиска бесполезно. Пусто ⇒ в ход идёт имя.
  - **Прогон только ручной** — каждый кадр это обращение к платной модели; автозапуска после аплоада нет намеренно (в отличие от проверки поворота). Кнопки в `/admin`: по дропу (`POST /api/ingest/drops/{id}/artifacts`, `?recheck=true` — пройти и уже проверенные) и **по всему архиву** (`POST /api/ingest/artifact-scan`) — путь «завели новый предмет, ищем его в старых дропах»; статус поллится `GET` тем же путём, что и запуск по дропу.
  - **Ручная рамка главнее находки модели:** `PUT /api/ingest/drops/{id}/photos/{photoId}/artifacts/{artifactId}` ставит/двигает рамку и помечает её `manual` — перепрогон перезаписывает только строки с `source = llm`.
  - **Снятие рамки — решение, а не косметика.** `DELETE` тем же путём помечает находку `rejected`, но **строку не удаляет**: удалённую пару следующий прогон нашёл бы заново и рамка вернулась бы. Отклонённые не рисуются нигде (ни публично, ни в админке) и не предлагаются повторно; координаты сохраняются — по ним видно, что модель принимала за предмет. Обратный ход: ручная рамка на ту же пару перезаписывает отклонение в `manual`.
  - **Рамка шире находки на 15% с каждой стороны**, и запас накидывается **при отрисовке**, а не в данных: в БД лежит то, что ответила модель, поэтому величину запаса можно менять без перепрогона (DESIGN §7.5).
  - **Ложные срабатывания — свойство задачи, а не дефект.** Описание артефакта задаёт **класс** предмета («чёрные обтекающие очки»), поэтому чужая похожая вещь под него подходит; замерено, что предмет с приметным рисунком (футболка с принтом) отделяется от чужих надёжно, а внешне типовой (очки) — нет. Лечится уточнением описания и снятием рамки руками; усиление (верификация по кропу, сравнение с фотографией предмета) — задел.
  - **AC:** сбой провайдера **не** помечает кадр проверенным — «не смогли проверить» и «проверили, ничего нет» разные состояния, иначе один простой Gemini записался бы как отсутствие артефактов и кадр больше не искался бы (та же защита, что у пустого прогона Health, §5.4).

Артефакты на кадрах: сущность `ArtifactDetection` (кадр × артефакт + доли `x0/y0/x1/y1` + `source` `llm|manual`), на `FilmPhoto` — `artifactsCheckedAt`, на `Artifact` — `detectionHint`; `ArtifactDetector` (чистый разбор ответа: имена предметов уезжают в промт списком ⇒ **один вызов на кадр независимо от числа артефактов**; координаты просим `[ymin, xmin, ymax, xmax]` в шкале 0..1000 как у Gemini, но разбор защитный — доли 0..1, выход за кадр и вывернутые углы переживаются) + `ArtifactDetectionService` (фоновые прогоны в один воркер с троттлингом `danchuo.film.artifacts.throttle-ms`). Находки едут в публичной проекции кадра (`FilmPhotoView.artifacts`).

### 5.13. Велопоездки (Велобайк)
**Описание.** Поездки на городском велошеринге **Велобайк** (Москва) как ещё один живой слой жизни. Источник — API мобильного приложения `pwa.velobike.ru`, восстановленный реверс-инжинирингом (публичного API нет, как у Вуша/Юрента, но контракт приложения вытащен). Слайс `bike` изолирует источник (как Spotify). На борде — **вертикальный виджет последней поездки** + список прошлых (DESIGN §7.6).

**Acceptance criteria:**
- **Чтение (публичное):** `GET /api/rides` — поездки (новые сверху): дата (MSK), длительность, дистанция, калории, тип велосипеда, тариф, точки старта/финиша. Отдаёт поездки **текущего календарного года** (MSK) — велосезон жмётся к лету, поэтому осью выдачи выбран год, а не число последних. Если в этом году поездок ещё нет (зима/начало года), возвращается **одна** самая свежая (последняя прошлого сезона), чтобы тайл не пустовал. Хранятся все запушенные. `GET /api/rides/stats` — агрегат (сколько накатал), считается по **всей** истории, а не по видимому году. `GET /api/rides/month-summary` — сводка за **текущий календарный месяц** (MSK): число поездок, суммарные минуты и **реально уплаченные за месяц деньги** (см. виджет ниже). До первого ingest — пустое состояние, не ошибка.
- **Виджет последней поездки:** мини-карта старт→финиш (две точки + пунктир «по прямой» — трека маршрута API не отдаёт), основные цифры, относительное «когда». **Адреса станций на тайле не показываются** — они живут только в модалке. **Модалка поездок** открывается двумя входами — **кликом по мини-карте** тайла ИЛИ кнопкой **«предыдущие»**: сверху прилипшая карта **выбранной** поездки, под ней — **прилипшая сводка за текущий месяц**, а ниже прокручиваемый **выбираемый список** всех поездок (строка — метрики + **стоимость поездки** справа от ккал + адреса станций, если есть; по умолчанию выделена самая свежая); выбор строки динамически перерисовывает карту. **Сводка месяца** (прикреплена к нижнему краю карты, со списком не скроллится) — три числа за **текущий календарный месяц** (MSK): сколько поездок, сколько минут суммарно и сколько денег потрачено; если в этом месяце поездок нет — строки нет вовсе. **Деньги — это фактически уплаченные за месяц суммы, а не сумма стоимостей строк:** платные поездки (`cost > 0`) плюс покупки тарифов-пакетов, сделанные в этом месяце (`bike_tariff`, каждая учтена ровно один раз). Так деньги **не задваиваются**: четыре бесплатные поездки «в рамках тарифа за 399 ₽» — это ровно 399 ₽ из одной реальной покупки (или 2×399, если куплено два пакета подряд), а не 4×399 из строк поездок. Стоимость показывается только в модалке (на тайле её нет). **Бесплатная поездка (`cost = 0`) — это, как правило, не «бесплатно», а поездка в рамках ранее купленного тарифа-пакета минут:** такие строки показываем как **«в рамках тарифа за N ₽»**, где N — цена ближайшей предшествующей покупки тарифа (см. следующий пункт). Если покрывающей покупки в истории не нашлось — остаётся честное «бесплатно». На большой карте наведение на пин старта/финиша показывает **адрес станции** (если он есть). Контур окна — как у фото-дропов.
  - **Про адреса (обогащение):** списочный `GET /api/rent/rents/client` отдаёт координаты и внешний id парковки, но **не адрес станции**. Адрес несёт только детальный `GET /api/rent/v2/rents/getPopulatedRent/{id}` (поля `startParkingAddress`/`finishParkingAddress` — имена станций, напр. «ст. м. Молодёжная (выход № 2)»). Поэтому букмарклет после сбора истории **дозапрашивает `getPopulatedRent` по каждой поездке** (пачками по 5, с прогрессом «адреса: X из Y») и подставляет адрес в элемент перед отправкой на ingest — всё в том же одном тапе. Поля совпадают с `RentItem`, маппер бэка читает их как есть (бэк не менялся). Сбой детали не роняет импорт: адрес остаётся пустым, поездка уходит без него. Велобайк в основном **станционный** (велосипед берут и возвращают на парковке-станции), и тогда старт/финиш — реальная станция с адресом. Но велосипед бывает оставлен **вне именованной станции** — в этом случае `getPopulatedRent` отдаёт вместо адреса **заглушку «просто город»** (литеральную строку «Москва»); признак заглушки — одно слово без цифр и запятых. Такой «адрес» не геокодится (см. следующий пункт), а витрина показывает вместо него честное **«вне станции»** (`formatStationAddress`).
  - **Про точки на карте (геокодинг станций):** мини-карта рисует пины по координатам старта/финиша, но у Велобайка это **сырой GPS велосипеда** (`*BikeGeoPosition`), который в Москве регулярно «улетает» (частый заброс в Шереметьево — GPS финиша уезжает к 55.95/37.42, хотя станция «метро Кунцевская» рядом). Координат самой станции Велобайк наружу не отдаёт (API парковок — `403` для роли CLIENT, датасет грузится непрозрачно). Зато **адрес** станции надёжен, поэтому его **геокодим** (OSM Nominatim) в координаты и рисуем пин по станции; сырой GPS остаётся фолбэком. Геокодинг — на бэке, фоном по одному адресу за тик (укладываемся в usage policy Nominatim), результат кэшируется по адресу (`bike_station`, §7) и больше не запрашивается; уникальный адрес геокодится один раз. Сбой геокодера деградирует тихо — точка остаётся на GPS. Фронт не меняется: координаты в `GET /api/rides` просто становятся корректными. **Адрес-заглушку «просто город» («Москва», велосипед вне станции) геокодер не трогает** (`StationGeocoder.isCityPlaceholder`, сразу `found = false`): Nominatim отдал бы центроид города (Красная площадь), который перекрыл бы **точный** GPS — у поездок вне станции GPS как раз надёжен (велосипед реально стоял в этой точке). Уже закэшированные заглушки сброшены миграцией в «не найдено».
  - **Про тарифы (атрибуция бесплатных поездок):** страница `purchases/history` отдаёт историю **покупок**, смешивая записи двух видов по полю `purchaseType`: `TARIFF` — покупка тарифа (напр. «Доступ Пакет 60 минут» = 399 ₽, «Доступ Поминутный» = 40 ₽; `cost` в копейках, `createDate` — момент покупки) и `RENTAL` — списание за конкретную поездку (это у нас уже есть в поездках). Тем же **одним** заходом букмарклет листает `purchases/history` и оставляет только `TARIFF`, кладёт их в буфер рядом с поездками (`{rides, tariffs}`). Бэк хранит покупки тарифов в сущности `BikeTariff` (§7) и к каждой бесплатной поездке подцепляет **ближайшую предшествующую по времени** покупку (`purchasedAt <= startTime`) — её цену и показывает как «в рамках тарифа за N ₽». Отдельным тайлом покупки не отображаются (уточняют только слово «бесплатно» в истории поездок).
  - **Про кадрирование карты:** карта подгоняет кадр под свои точки при КАЖДОМ изменении размера контейнера, а не только при открытии. Иначе подобранный однажды zoom-level Leaflet при росте контейнера (большой монитор, уменьшенный масштаб браузера) сохраняет масштаб и показывает больше пустоты вокруг — точки съезжаются к центру и карта «отдаляется». Пины при этом остаются фиксированного размера намеренно — DESIGN §8.1.
- **Приём (за bearer):** идемпотентно по `externalId` (поездки — id аренды, покупки тарифов — id платежа); повтор не плодит дубли. Каналы поездок: (1) **push** `POST /api/ingest/bike/rides` — массив поездок из уже авторизованного браузера/шортката (обходит Qrator); (2) **серверный поллинг** — SMS-логин (`/authorize/code` → `/authorize`) сохраняет refresh-токен шифрованно, фоновый поллер тянет историю. Покупки тарифов принимает `POST /api/ingest/bike/tariffs` — массив записей `purchases/history`; записи `RENTAL` бэк отсеивает сам, хранит только `TARIFF`.
- **Импорт из браузера (реализованный основной канал):** букмарклет запускается внутри залогиненной PWA `pwa.velobike.ru` (сессия уже прошла Qrator), **одним заходом** собирает поездки (с адресами) и покупки тарифов и **копирует в буфер объект `{rides, tariffs}`**; владелец вставляет JSON в `/admin → поездки велобайк`, откуда POST-ы на push-эндпоинты идут **с того же origin** (токен записи не покидает danchuo.world). Никакого CORS и никаких секретов на чужом origin; запасной путь при строгом CSP — тот же сниппет в консоли DevTools. Обратная совместимость: голый массив поездок (старый формат) админка тоже принимает.

**Technical considerations.** Сущность `Ride` (§7). Авторизация Велобайка — SMS-код → JWT (access 24ч / refresh ~6 мес), refresh шифруется at-rest (§8, как Spotify). **Геоданных только старт и финиш** — трека нет (карта рисует 2 точки). **Анти-бот Qrator** перед API режет датацентр-IP: серверный поллинг с VPS требует резидентного прокси, поэтому основной канал — импорт из браузера владельца (Qrator-free, см. выше). Авторизация PWA снята живьём с прода: access-токен Велобайка лежит в IndexedDB (`keyval-store`/`keyval`/`vb-access-token` — JWT `iss=client-oauth`), не в web-storage; сессионной куки API не принимает (без токена — 401). Букмарклет читает токен из IndexedDB и шлёт `Authorization: Bearer`. Карта — Leaflet + OSM-тайлы (без ключа). Подробности риска — §13.

### 5.14. Админ-панель (`/admin`)
**Описание.** Единственный приватный экран владельца — служебная страница в том же фронте: управление фото-дропами (§5.12) и просмотр хитмапы кликов (§5.11) на одном скроллящемся экране. Отдельного «служебного» дизайна у админки нет — она **красится стилем активной волны**, как публичный борд.

> **Статус.** Реализовано (B1 — дропы, B2 — хитмапа). Изначально админка несла фиксированный чёрно-белый скин, сознательно не следовавший волнам, — **снят**: теперь волны действуют и здесь, включая переключатель.

**Acceptance criteria:**
- **Доступ:** тот же статический bearer-токен, что у `/api/ingest/*` (§8); вводится один раз и живёт в `sessionStorage` вкладки, «выйти» стирает. Страница `noindex` и вне sitemap.
- **Экран логина:** минимальный — по центру экрана только поле токена и кнопка **«сыграть»**, без заголовков/подписей/плейсхолдера (доступное имя поля для скринридеров остаётся). Неверный токен или недоступная сеть — тихая строка ошибки под формой.
- **Скин:** админка следует активной волне — токены и ключ волны приходят из корневого layout (SSR: кука посетителя → активная волна владельца), затенения токенов внутри админки нет. В шапке залогиненного экрана — тот же переключатель волн, что на борде (§5.9): живой своп без перезагрузки, выбор запоминается в куку и действует на весь сайт.
- **Содержимое залогиненного экрана:** загрузка/управление дропами (§5.12) + секция хитмапы (§5.11). В сетке кадров дропа: клик по кадру — обложка; **кнопка ↻ в углу кадра** — ручной поворот на 90° за клик (не пересекается с кликом-обложкой); кнопка «проверить поворот» — LLM-прогон с живым статусом (§5.12, B9); кадры, где LLM не определилась, помечены бейджем «?».
- Бикон аналитики **не трекает `/admin*`** — клики владельца не мусорят статистику (§5.11).

**Technical considerations.** Волны в админке — не отдельный механизм: `admin/layout.tsx` резолвит отображаемую волну тем же путём, что главная (`fetchDisplayTheme`, single-flight на запрос), и оборачивает страницы в общий `WaveProvider`; скин-CSS волн (`[data-wave]`) глобален и действует на админку автоматически. Локальный `admin.css` держит только нейтральную панель на токенах (`.admin-panel`) — никаких переопределений палитры.

### 5.15. Вклады GitHub («активность другого рода»)
**Описание.** День несёт число **вкладов на GitHub** — то же, что рисует календарь профиля: коммиты + PR + ревью + issue. На борде это одна цифра: чип **«+N»** в плитке «активность» (DESIGN §7.4), отвечающий на единственный вопрос — **был ли сегодня гит**. Отдельного виджета нет и не планируется; собранная история при этом полная и ждёт линзы календаря (§9 I-19).

**Считаем вклады, а не коммиты.** При конвенции разработки «одна ветка = один коммит» число коммитов систематически занижает день, в который приземлилась крупная фича (она — один коммит), и завышает день мелких правок. Вклады целиком ближе к «сколько работы доехало».

> **Канал — публичная страница, а не API, и это единственный рабочий вариант.** Открытого эндпоинта под календарь у GitHub нет: REST его никогда не отдавал, а GraphQL, где живёт `contributionsCollection`, требует токен на **каждый** запрос (без него — 403). Публичная лента событий (`/users/{login}/events/public`) не годится отдельно: приватные репозитории в неё не попадают, а у владельца там вся работа — замер 31.07.2026 дал 19 событий, из них **один** push, при 390 вкладах за год. Остаётся HTML-фрагмент `github.com/users/{login}/contributions`, которым профиль рисует свою же сетку: год клеток с точными числами в подписях, **включая приватные вклады**, без токена вовсе.

**Три следствия, которые легко принять за баг:**
- **Границу суток назначает GitHub, мы её не пересчитываем.** Он раскладывает вклады по UTC, поэтому коммит в 01:00 MSK 1 августа лежит в 31 июля. По календарным суткам MSK это расхождение, но по дню владельца (§4: день идёт с 7 утра до 2–3 ночи) — попадание: ночной коммит и правда хвост уходящего дня. Перебить корзину всё равно нечем — фрагмент отдаёт уже разложенные дни.
- **Зависит от настройки профиля** «Include private contributions on my profile». Выключить её — значит обнулить канал: цифры схлопнутся до публичной активности.
- **Разметка может поехать.** Она уже менялась однажды (числа переехали из атрибута ячейки в текст всплывающей подписи). Поэтому разбор пессимистичный, а сбой ведёт к молчанию, не к нулям (см. AC ниже).

**Acceptance criteria:**
- Сбор фоновый (`@Scheduled`, дефолт 30 мин), токена не требует; выключается конфигом (`danchuo.github.enabled`), логин настраивается (`danchuo.github.username`).
- Один заход забирает **год клеток разом** ⇒ первый же прогон дозаполняет всю прошлую историю; ждать накопления не нужно.
- `null` ≠ `0` строго: `null` = «день не собирали», `0` = «собрали, вкладов не было». Нулевых дней много, различие рабочее.
- **Не разобрали — не пишем.** Сеть, страница ошибки, поехавшая разметка дают пустой разбор, и прогон не трогает ни одного дня: «не смогли достать» и «вкладов не было» по данным неразличимы, а первое случается чаще (та же доктрина, что «пустой прогон Health не стирает ночь», §5.4).
- Записывается только **изменившееся** — иначе каждые полчаса дёргался бы `updatedAt` у трёх сотен строк. Дни раньше генезиса и **позже сегодня** отбрасываются (хвост текущей недели приходит клетками «вкладов нет» — заводить будущие дни в базе незачем).
- Сбор **не двигает индикатор свежести** (§8): лампа отвечает на «когда с телефона приезжали данные», а сборщик, ходящий наружу сам, держал бы её вечно на «только что».
- Чип показывает вклады **выбранного в календаре дня** (как и оба читаута плитки) и **молчит на нуле и на «не собирали»** — ежедневный «+0» был бы шумом.
- Цвет чипа — токен волны `--accent-code` (DESIGN §2.1), не зелёный литерал: своя палитра у каждой волны.

**Technical considerations.** Слайс `github` (внешний источник изолирован, как `spotify`/`bike`): REST-клиент `GithubContributionsApi` (HTML), чистый `ContributionCalendarParser` (вся хрупкость канала заперта в нём — атрибуты читаются по одному, связь «ячейка ↔ подпись» по `id`/`for`, непонятое молча выпадает; уровень заливки `data-level` в счёт не переводится — «примерно 3» борду не нужно), чистый `ContributionWriteFilter` (генезис/будущее/без изменений) и `GithubContributionCollector` (планировщик + запись). Поле — `DayRecord.contributions` через `DayRecordService.applyContributions` (единая точка записи), наружу едет в `DaySummary`. Регрессионный якорь парсера — срез **живой** разметки в фикстурах: поедет вёрстка у GitHub — упадёт тест, а не прод.

## 6. Дизайн-система

PRD держит функциональные требования и acceptance criteria; `DESIGN.md` отвечает «как это выглядит и ощущается».

> **Сленг волны** (унифицированные термины: волна, токены, активная волна, декоративный слой, акцент дня) — `DESIGN.md` → «Сленг волны». **Пиксельность — свойство волны 01, не продукта:** в продуктовых спеках PRD визуал описывается нейтрально («стиль активной волны»); пиксель упоминается только в явном разговоре о волне 01.

Ключевые опорные точки (детали — в `DESIGN.md`):
- **Волна 01 «Студия/Персик»:** тёплый персик + сдержанный пиксельный декоративный слой. Анти-slop = реальные данные + характер волны.
- **Bento:** холст 20×20, видимый борд без скролла — верхние 14 строк (20×14).
- **Акцент дня:** метка дня (наличие имени); отрисовка — по стилю активной волны (волна 01 — пиксель-точка снизу ячейки). Вкус монстра меткой дня не является (5.3).
- **Состояния:** per-tile loading/empty/error, общего спиннера нет.
- **Примеры раскладки:** `../examples/` (десктоп + мобайл вайрфреймы волны 01).

### Acceptance criteria волны
- Токены заданы в БД (JSONB) и инжектятся в `:root`; ни одного хардкод-цвета в компонентах.
- Волна вправе нести **скин** (`[data-wave]`-CSS): своя форма карточек/фон/декор/шрифт — не только цвета (§5.9 «три слоя», DESIGN §10.2). Скин одной волны не протекает в другие (всё под селектором `[data-wave="<key>"]`).
- Тема проходит контраст (текст на `--bg-page` и на `--bg-surface` — AA).
- Пиксельный слой соблюдает правило сдержанности волны (`DESIGN.md` §1): нет пикселя в основном тексте/цифрах-данных (правило каждой волны своё; волна 02 пускает пиксель-шрифт на метки, но не на данные).

## 8. Кэширование, лимиты и эксплуатация

- **Кэш:** `quarkus-cache` (Caffeine, in-process). Кэшируем now-playing (~20с), recent/top (минуты), агрегаты дня и активную тему (инвалидация при ingest/смене темы). **Redis не нужен**, пока один инстанс; оправдан при мульти-инстансе / персистентности кэша / шаринге лимитов — или как осознанное «хочу пощупать» (бэклог).
- **Рейтлимит / анти-абуз:** L7-лимиты в Caddy + точечные лимиты на публичные GET и телеметрию `POST /api/analytics/*` через **собственный in-memory токен-бакет на IP** (`RateLimitFilter` в `core`; раздача `/api/film-media` исключена). Важно: это останавливает одного шумного клиента, **не настоящий DDoS** — для последнего в бэклоге **Cloudflare free (без капчи)** перед сайтом.
- **Сборка:** JVM-jar (быстрый дев, `backend/Dockerfile`) + native-image (прод, `backend/Dockerfile.native`: GraalVM/Mandrel jdk-25; `quarkus-awt` — ImageIO фото-дропов в нативе, `quarkus-smallrye-health` — `/q/health` для смоука и деплой-гейта; Response-обёрнутые проекции помечены `@RegisterForReflection`).
- **Деплой:** `docker-compose.prod.yml` (caddy + frontend + backend-native + postgres; секреты из `/opt/danchuoworld/.env`, в compose — `${…:?}` без дефолтов). GitHub Actions `deploy.yml`: push в `main` → native-бэк + Next-фронт → GHCR (теги `latest` + sha коммита; sha = ручной откат) → **смоук живых контейнеров** (health-готовность, загрузка zip через весь AWT-пайплайн, проверка формы JSON публичных проекций, фронт SSR против бэка) → ssh-деплой (`compose pull && up -d`) с health-гейтом. Native-сборка и смоук — только в CI: VPS ничего не собирает. Миграции Liquibase перед 1.0.0 консолидированы начисто (12 файлов `0010`–`0120` = финальное состояние; прод стартует без исторических промежуточных апдейтов). Чеклист выката/отката — `docs/deploy.md`.
- **Мониторинг свежести:** хранить `lastIngestAt`; в UI — тихий индикатор свежести; простой алерт (напр. в Telegram), если данные «застряли» дольше N часов — иначе молчаливо устаревший дашборд.
- **Бэкапы (бэклог):** cron на VPS → дамп Postgres → Google Drive (offsite).

Выбор — рантайм-свойство `danchuo.llm.provider` (`groq` по умолчанию), потому что при смене провайдера меняется ключ, а не код; неизвестное значение откатывается на Groq с варнингом, чтобы опечатка в env не роняла сайт. Реализации помечены `@Typed` своим классом — иначе два бина типа `LlmClient` дают неоднозначность инъекции; единственный бин этого типа — делегат `ConfiguredLlmClient`. Без ключа — тихая деградация в `null`, вызывающие не падают. Ключи — env `DANCHUO_LLM_API_KEY` (Groq) и `GEMINI_API_KEY`.
>
> **Почему появился второй провайдер.** Groq вывела из обращения vision-модель `llama-4-scout`: любой запрос с ней возвращает 404, который клиент по контракту превращает в `null`, — то есть **проверка поворота кадров (B9) молча перестала работать**, выглядя как «модель не смогла решить». Единственная оставшаяся у Groq vision-модель `qwen3.6-27b` требует `reasoning_effort: none` (иначе тратит весь лимит ответа на размышления и обрывается, не дойдя до JSON) и, по замеру на живых кадрах прода, **непригодно указывает координаты** — рамка систематически уезжает выше цели, и второй проход зумом это не лечит (смещение задаётся относительно поданного изображения и воспроизводится на каждом увеличении). Gemini отдаёт координаты как часть контракта — строгой JSON-схемой, в шкале 0–1000 и в порядке `[ymin, xmin, ymax, xmax]`, **y первым**. Отсюда `completeVisionJson`: провайдер, умеющий структурный ответ, ограничивает его схемой; остальные откатываются на обычный `completeVision`, поэтому разбирать ответ всё равно надо защитно.

## 10. UI-принципы

- **Календарь — главная навигация:** ховер = превью, клик = перефокус «Сегодня»; на тач — тап.
- **Bento**, «Сегодня» — крупная центральная плитка; по периферии мелкие виджеты.

- **Артефакты — marquee с подписями;** «монстр»/пункты чеклиста — акценты на днях.
- **Mobile-first и тач:** все hover-взаимодействия имеют тап-эквивалент; уважать `prefers-reduced-motion`.
- Плотность держать под контролем — не пихать всё на главный экран.

## 11. Безопасность и приватность

- **Транспорт:** только HTTPS (Caddy + Let's Encrypt).
- **Запись:** мутирующие эндпоинты (`/api/ingest/*`, будущая admin) — за статическим bearer-токеном; GET публичны.
- **Секреты at-rest:** Spotify refresh-токен и прочие секреты — шифрование на уровне колонки (ключ из env); опц. full-disk на VPS (накладные пренебрежимы).
- **Токен записи:** в секретах шортката и серверном env, не в репо; лёгкая ротация.
- **Аналитика:** cookieless, **без сырого IP** (только суточный хэш) → как правило, cookie-баннер не нужен (не юрист — при сомнениях свериться). Сырьё хранится минимально необходимое.
- Контент публичен на чтение → главный объект защиты — **креды записи**, не сами статы.

- **Смарт-пунктуация iOS** превращает `"` в `“ ”` → битый JSON. Отключить: Настройки → Основные → Клавиатура → Smart Punctuation OFF (хотя бы на время редактирования).
- Get Contents of URL / Get Dictionary Value **сами подхватывают выход предыдущего действия** — все входы-чипы проверять тапом (подсвечивается действие-источник) и перевязывать через Select Magic Variable.
- Словарь (Dictionary) как источник Choose from List выглядит красивее списка, но выбранные элементы — «элементы словаря», а не текст: лукап Get Dictionary Value по ним молча возвращает пусто. Поэтому схема на **List с готовыми фрагментами** — без маппинга нечему ломаться.
- Новый вкус монстра = `INSERT INTO monster_flavor` (data-driven, без релиза) + строка в List шага 5.

Запуск: иконка на домашнем экране / **кнопка действия** (Настройки → Кнопка действия → Быстрая команда) / автоматизация-напоминание по времени. Повторный прогон за тот же день безопасен (семантика — §5.6).

### А.2. «Health авто» — шаги и сон

Авто-съём Apple Health (§5.4) → `POST /api/ingest/health`. Запуск — time-automations (12:00 / 18:00 / 24:00 MSK), без ввода; повторный прогон идемпотентен (upsert за дату). Схема v2 (2026-07-28); v1 считала сон прямо в шорткате и теряла куски ночи до полуночи — история и разбор ниже.

> ⚠️ **Автоматизации сняты владельцем (2026-07-28).** Причина — последняя грабля этого списка: к заблокированному телефону шорткат в Health не достучится, а фоновая автоматизация об этом молчит, отчитываясь «выполнено». Слот «24:00» не срабатывал почти никогда. Рабочий путь сейчас — ручной прогон **А.2.1**; схема ниже сохранена как основа для него (А.2.1 — её дубликат с вводом даты) и на случай возврата автоматизаций.

**Принцип v2: шорткат не считает сон.** Он выбирает семплы за заведомо широкое окно и перекладывает их как есть — `{фаза, начало, конец}` за каждый кусок. Ночь собирает бэк (§5.4): группирует куски в сессии и берёт ту, что **закончилась** в целевой день. Отсюда: ширина окна не настройка (перебрать безопасно, недобрать нельзя), фазы не надо суммировать по веткам `If`, а Value семпла — текст фазы — идёт в JSON текстом, куда он и просился. Осталось 16 действий вместо 42.

**Порядок сборки (v1 не чинится, а выбрасывается).** С v1 общие только шаги 1–3 (шаги) — сонная часть меняется целиком, хирургия по 42 действиям дольше и опаснее сборки с нуля. Собирать удобнее **не эту команду, а А.2.1**: она надстройка (ввод даты + окна, отсчитанные от неё), её можно сразу проверить на известной ночи, а потом продублировать и снять ввод — получится А.2. Двумя командами это остаётся потому, что **Ask for Input в фоновой автоматизации молча убивает выполнение**.

**Грабли, уже собранные (не повторять):**
- **Почему v1 теряла ночь.** Фильтр стоял `End Date is today`: куски, закончившиеся до полуночи (уснул 23:20), в выборку не попадали, и ночь показывалась «с 00:00» — минус вечерний хвост и из длительности, и из фаз. Фильтр по `Start Date is today` симметрично терял бы всё начало. Одной границей семпла ночь не выделяется в принципе — отсюда «широкое окно + сессии на беке».
- **Value сна — ТЕКСТ фазы** (`REM` / `Deep` / `Core` / `Awake` / `Asleep` — голые строки на англ. iOS), а не число. В v1 это было главной болью (любая Calculate Statistics по семплам сна давала «couldn't convert from text to number»); в v2 текст просто уезжает в JSON. Свойства чипа (`Value` / `Start Date` / `End Date`) выбираются тапом по вставленному чипу `Repeat Item`.
- **Смещение в формате дат** (`ZZZZZ` → `+03:00`) — чтобы время не поехало, если телефон окажется в другом поясе. Если устройство упрётся в этот паттерн, годится и `yyyy-MM-dd'T'HH:mm:ss`: бэк прочитает время без смещения как MSK.
- **«This action is trying to share N Health items which is not allowed».** Приватностный гард Shortcuts: iOS блокирует передачу наружу большого объёма Health-данных (порог ~100 семплов). Широкое окно v2 даёт под две сотни кусков за прогон, поэтому упирается всегда — в v1 с фильтром «за сегодня» его не было видно. Лечится тумблером **Настройки → Приложения → Быстрые команды → Дополнительно → «Разрешить отправку больших объёмов данных»** (*Allow Sharing Large Amounts of Data*; на iOS ≤17 — Настройки → Быстрые команды → Дополнительно). Тумблер глобальный, на приложение. Ужимать окно ради обхода не стоит: полутора суток хватает по смыслу, но семплов остаётся впритык к порогу и на длинной ночи он стрельнёт снова.
- **Format Date у End Date легко забыть.** Новый `Format Date` встаёт с локальным «Short» форматом: `start` уезжает как `2026-07-28T01:00:36+03:00`, а `end` — как `28.07.2026, 01:13`, и приём валится 400 по `sleepSegments[0].end`. Custom-паттерн нужен обоим действиям, оба поля в теле обязаны выглядеть одинаково.
- **Обязательная строка фильтра в Find Health Samples тихо режет выборку.** Первую строку условия удалить нельзя, и по умолчанию в ней стоит `Start Date` → **is in the last 7 days**. С `Where All` она сцепляется с нашим диапазоном по `End Date` логическим И — и в пересечении остаётся мусор: за 20 июля выживает одна ночь (та, что началась позже «сегодня − 7»), за 19-е пересечение пустое и приходит ноль кусков. Диагностируется тем, что число семплов подозрительно мало и все из одной, самой свежей ночи окна. **Лечение: в обязательной строке тоже поставить `is in the range` с теми же чипами окна** (в А.2 — `Current Date − 36 Hours` → `Current Date`). Достаточно и одной границы — бэк выбирает день по концу сессии сам, окно шире суток с обеих сторон, поэтому ночь лежит внутри него целиком, — но два одинаковых условия надёжнее: удалять всё равно нечего, а расходиться нечему.
- **Пустой прогон больше не стирает ночь.** Пустой список кусков неотличим по данным от «не спал», а причин у него хватает (заблокированный телефон, промах окна, съехавшая дата) — раньше такой прогон затирал уже записанный сон в «нет данных». Теперь при пустом результате сон **не трогается**, а ответ несёт `"sleepSkipped": true`; право стереть ночь осталось только у явного `sleepMinutes = 0` (легаси-форма). В ответе также едет `"sleepMinutes"` — то, что реально записалось: `Show Result` на телефоне сразу показывает, сработал прогон или прошёл вхолостую.
- **Ночь без семплов.** Repeat не выполнится ни разу, Combine Text отдаст пусто, уедет `"sleepSegments":[]` — бэк запишет «сна не было» (правильно). Если Shortcuts заартачится на неинициализированной переменной `Chunks` — вместо разделителя `,` собрать элементы с **запятой в конце** каждого (шаг 9) и разделителем **none**, а в шаге 13 закрыть массив фиктивным элементом: `[«Segments»{"stage":"In Bed","start":"2000-01-01T00:00:00+03:00","end":"2000-01-01T00:00:00+03:00"}]` — `In Bed` бэк не считает сном и пропускает.
- **Дубли источников больше не проблема** (Find Health Samples не дедуплицирует семплы, Health в интерфейсе — дедуплицирует): бэк разбирает перекрытия по времени, ночь не удваивается. Фильтр **Source** в Find добавлять не нужно. Селф-чек прежний: длительность сходится с Health → Sleep → Time Asleep (±1 мин).
- **Ночь без часов** iPhone пишет одним семплом `Asleep` без фаз — в v1 он не попадал ни в одну ветку `If` и сон уходил нулём; теперь считается как light, длительность честная.
- **Полуночный прогон.** `date` и фильтр шагов считаются от Current Date — автоматизацию «24:00» ставить строго до полуночи, иначе они уедут на завтра. Сна это больше не касается: его окно скользящее.
- Смарт-пунктуация и молча перевязывающиеся чипы — общие грабли из А.1 действуют и здесь.
- `workouts` API принимает (§5.4), но в текущей сборке они не отправляются — бэклог шортката.
- **Заблокированный телефон = пустой прогон.** Данные Health зашифрованы и недоступны, пока iPhone заблокирован: time-automation честно отчитывается «выполнено», но Find Health Samples возвращает пусто (ошибок фоновые автоматизации не показывают). Слоты 12/18 обычно попадают на разблокированный телефон, «24:00» — почти никогда. **Из-за этого автоматизации в итоге и сняты** (врез в начале раздела); прогон делается руками — А.2.1.
- **«Осознанность» надо сперва включить.** Приложение «Журнал» пишет проведённое в нём время в Health, только если разрешено: **Настройки → Приложения → Журнал → Health Access → Mindful Minutes** (там же State of Mind). Без этого выборка ш.11а пуста всегда, и отличить это от «не вёл дневник» по данным нельзя.
- **Фильтр Source в осознанности обязателен** — в отличие от сна, где он не нужен. Mindful Minutes это общая корзина: туда же пишут «Дыхание» на часах и любое медитационное приложение, и 15 минут чужой медитации в 21:00 поставили бы галочку «дневник». Имя источника локализовано, поэтому фильтр ставится **в шорткате** (выбор из списка), а не на бэке по строке.
- **«Журнал» пишет россыпь коротких кусков, а не одну сессию** — открыл, закрыл, вернулся: в живых данных вечер выглядит как `22:49:52→22:52:45` + `22:53:23→22:56:58`. Бэк их просто складывает внутри вечернего окна (в сессии, как сон, не группирует — вопрос «сколько всего минут за вечер»). Отсюда практическое: **порог 15 минут набирается не так легко, как кажется** — если отметка не встаёт на днях, когда дневник точно вёлся, смотреть надо на `journalMinutes` в ответе и крутить `danchuo.journal.min-minutes`, а не искать баг.
- **Окно осознанности отдельно считать не надо.** Границы вечерней корзины (`19:00 → 02:00`) живут на бэке, а шорткату достаточно того же широкого окна, что уже отмерено для сна: 36 часов назад от «сейчас» (А.2) и «День −1 / День +2» (А.2.1) накрывают вечерние корзины целиком. Поэтому новых `Adjust Date` не появляется — переиспользуются те же чипы.

### А.2.1. «Health за дату» — ручной досыл

Догон пропущенных авто-прогонов и пересъём старых ночей: та же логика, но день выбирается на старте. **Это та команда, которую собирают первой** (А.2 — её дубликат без ввода, см. врез выше). Дельта от А.2:

| Отличие | Настройка |
|---------|-----------|
| Новый шаг 0а | **Ask for Input** (**Date**, не Date and Time) — Prompt «За какой день?»; в **Default Answer** — чип **Current Date**, тогда обычный прогон это один тап |
| Новый шаг 0б | **Adjust Date** — вход 0а, режим **Get Start of → Day**. **Обязательно, а не для красоты:** Ask for Input отдаёт выбранный день с ТЕКУЩИМ временем (запустил в 17:31 — получишь `20 июля 17:31`), и все окна ниже съезжают на эти часы. Результат ниже зову **«День»** |
| Новый шаг 0в | **Format Date** — вход «День», Date Format **Custom** → `yyyy-MM-dd`. Это значение уедет в тело запроса, отдельный Format Date в конце не нужен |
| Новый шаг 0г | **Adjust Date** — к «Дню» добавить **23 ч 59 мин** → конец дня (не «+1 день»: «is in the range» включает обе границы, семпл ровно в следующую полночь зацепился бы) |
| Шаг 1 (шаги) | условие **is today** → **is in the range** от «Дня» (0в) до 0г (чипы через Select Magic Variable); поле прежнее — Start Date |
| Шаги 4–5 (окно сна) | шаг 4 — **Adjust Date**: от «Дня» Subtract **1 Day**; добавить второй **Adjust Date**: от «Дня» Add **2 Days**. Оба считаются **от «Дня»**, а не друг от друга — если второй подхватит выход первого (действия делают это молча), окно уедет на сутки и ночь выбранного дня в него не попадёт. В шаге 5 **обе** строки фильтра — **is in the range** между ними (обязательная по `Start Date` и добавленная по `End Date`) |
| Шаги 11а–11д (осознанность) | **без изменений** — окно берётся теми же чипами, что и у сна («День −1 день» → «День +2 дня»), и накрывает вечерние корзины и выбранного дня, и предыдущего |
| Шаг 12 (Format Date) | удалить — его заменил шаг 0в; в теле запроса чип даты берётся с 0в |

Итого 25 действий. **Нормализацию делать именно `Adjust Date → Get Start of Day`**, а не кругом через текст: `Format Date` → `yyyy-MM-dd` → `Get Dates from Input` даёт **полдень**, а не полночь (парсер Shortcuts достраивает время у голой даты). Полдень коварен тем, что сон-то находится — окно «−1 день / +2 дня» ночь всё равно накрывает, — а вот окно **шагов** съезжает на половину следующих суток, и это заметно не сразу. Если режима `Get Start of` в сборке нет, текстовый круг годится только с явным временем в шаблоне: `yyyy-MM-dd'T'00:00:00`. Остальное байт-в-байт как А.2. Обратный переход (А.2.1 → А.2) — те же пять строк наоборот: снять 0а/0б, вернуть шагам `is today`, свернуть два Adjust Date в один (**Current Date − 36 Hours**), вернуть Format Date на Current Date. Бэкенд готов как есть: `date` — обязательное поле `POST /api/ingest/health`, окна валидации нет (в отличие от `/api/ingest/daily` с его [сегодня − 31, сегодня]), стоит только генезис-гард; ингест идемпотентен, повторный досыл за день безопасен. Health хранит историю — семплы прошлых дней достаются теми же Find Health Samples.

**Какое число выбирать.** День **пробуждения**, а не тот, под которым ночь показана в приложении Здоровье: Health подписывает её вечером засыпания, и расхождение составляет ровно сутки (§4). Ночь, которую Health зовёт «20 июля», досылается как **21-е**. Пустой результат при «правильном на вид» дне — первый признак, что взято число из Health.

**Дневник выбор даты не ломает.** Минуты «осознанности» раскладываются по вечерним корзинам **сами**, дата запроса на них не влияет (§4, §5.6) — поэтому число по-прежнему выбирается ради сна, а дневник встанет на своё место. Практическое следствие: досылая «21-е» ради ночи, вечернюю галочку получит **20-е** — это верно, вечер-то был двадцатого. Проверяется по `journalMinutes` в ответе: там дни подписаны явно.

**Пересъём прошлых ночей.** Ночи, залитые v1, лежат в БД обрезанными — их надо просто досылать заново этой командой за нужные даты: ingest идемпотентен, значения перезапишутся полными.
