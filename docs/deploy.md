# Деплой danchuo.world на VPS

Схема (PRD §8, M0): **GitHub Actions собирает образы и деплоит, VPS только запускает.**
Native-сборка Quarkus требует 6–8 GB RAM — она живёт на CI-раннере; на сервере всегда
только `docker compose pull && up -d`.

```
push в main ──> Actions: native-бэк + Next-фронт + edge-caddy ──> push в ghcr.io
                       └──> smoke: контейнеры реально гоняются (health + фото-пайплайн)
                       └──> validate: Caddyfile парсится НАШИМ образом caddy
                       └──> ssh на VPS ──> docker compose pull && up -d ──> health
```

**Образов три, не два.** `caddy` собирается из `caddy/Dockerfile` (stock `caddy:2` + модули
`caddy-ratelimit` и `cache-handler`) и тегируется той же sha, что бэк и фронт. Причина —
`Caddyfile` использует директивы `rate_limit` и `cache`, которых в стоковом Caddy нет: он такой
конфиг даже не распарсит. Практическое следствие, о которое легко споткнуться: **валидировать
Caddyfile через `caddy:2` больше нельзя** — она покраснеет на исправном файле. Оба шага
валидации (в CI и на VPS) бьют по нашему образу.

Стек на VPS: `caddy` (единственный наружу: 80/443, авто-TLS) → `frontend` (Next SSR) +
`backend` (Quarkus native) → `postgres`. `/api/*` Caddy ведёт **напрямую в Quarkus**,
мимо Next — большие zip фото-дропов не упираются в прокси-лимиты.

## Соседство с proxemics (тот же VPS)

Стеки полностью изолированы: свой compose-проект `/opt/danchuoworld` (сеть/тома/имена),
из хост-портов заняты только 80/443 (caddy) и loopback `127.0.0.1:8081` (health/туннель) +
`127.0.0.1:5433` (psql) — proxemics держит loopback 8080/5432, пересечений нет.
`docker image prune -f` в конце деплоя чистит только dangling-слои — чужие образы не трогает.

## 1. Разовая настройка VPS (руками, один раз)

Docker + базовая гигиена уже сделаны для proxemics — переиспользуем.

- [ ] `mkdir -p /opt/danchuoworld` — compose и Caddyfile туда дальше кладёт сам Actions.
- [ ] **`/opt/danchuoworld/.env`**, права `chmod 600` — единственное место прод-секретов:
      ```
      POSTGRES_PASSWORD=...            # openssl rand -base64 24
      DANCHUO_INGEST_TOKEN=...         # openssl rand -base64 24; его же — в iOS-шорткаты
      DANCHUO_ANALYTICS_SALT=...       # openssl rand -base64 24
      DANCHUO_TIME_GENESIS=2026-01-01  # реальная генезис-дата данных
      # Spotify (опционально — без них слайс «не сконфигурирован»)
      DANCHUO_SPOTIFY_CLIENT_ID=...
      DANCHUO_SPOTIFY_CLIENT_SECRET=...
      DANCHUO_SPOTIFY_TOKEN_KEY=...    # ТОТ ЖЕ ключ, каким шифровался сохранённый refresh-токен
      # WebDAV полки читалки (§5.16) — ОБЯЗАТЕЛЬНЫ: без них compose не поднимется.
      # Этот же логин/пароль вбивается в Anx Reader на телефоне (адрес https://danchuo.world/dav).
      WEBDAV_USERNAME=danchuo
      WEBDAV_PASSWORD=...              # openssl rand -base64 24
      # Велобайк (опционально; поллер выключен по умолчанию)
      DANCHUO_BIKE_PHONE=...
      DANCHUO_BIKE_TOKEN_KEY=...
      # LLM (опционально — без ключа слайс llm тихий no-op, проверки помечают кадры пропущенными)
      DANCHUO_LLM_API_KEY=...          # Groq: тот же ключ, что у proxemics
      GEMINI_API_KEY=...               # Gemini: платный ключ, только он ставит рамки по месту
      DANCHUO_LLM_PROVIDER=gemini      # без этого поиск артефактов уйдёт в Groq и словит 429
      ```
      ⚠️ **`DANCHUO_LLM_PROVIDER` и `GEMINI_API_KEY` — пара.** Ключ без переключателя не
      используется вовсе: провайдер по умолчанию `groq`, и весь поиск артефактов (§5.12)
      молча упрётся в его рейт-лимит. Симптом ровно такой: прогон идёт, находок нет,
      в логах бэка `Groq request failed: ... 429`. Данные при этом целы — кадр без ответа
      модели остаётся непроверенным, а не «проверенным, пусто».
- [ ] **Деплой-ключ для Actions**: отдельная SSH-пара только для этого репо
      (`ssh-keygen -t ed25519 -f deploy_key`), публичный → `~/.ssh/authorized_keys` на VPS,
      приватный → секрет GitHub (§2). Ключ proxemics не переиспользуем.
- [ ] **ghcr.io**: на VPS уже есть `docker login ghcr.io` от proxemics (тот же владелец,
      scope `read:packages`) — новые пакеты подтянутся им же. Альтернатива — сделать
      пакеты публичными.
- [ ] **Бэкапы**: по образцу `proxemics/ops/backup.sh` — дамп постгреса danchuoworld
      (`docker exec danchuoworld-postgres pg_dump ...`) **плюс том `filmdata`**
      (кадры фото-дропов — единственные невоспроизводимые файлы).

## 2. GitHub (репозиторий)

- [ ] **Секреты Actions** (Settings → Secrets and variables → Actions):
      - `VPS_HOST` — IP/домен сервера
      - `VPS_USER` — пользователь деплоя
      - `VPS_SSH_KEY` — приватный деплой-ключ из §1
      (для push в ghcr.io хватает встроенного `GITHUB_TOKEN`)
- [ ] Сделать чеки `pr-build.yml` required в branch protection — в `main` (= в прод)
      не попадает красное.
- [ ] Workflow уже в репо: `.github/workflows/deploy.yml` — на push в `main`, три этапа
      (сборка → smoke → ssh-деплой). Тесты гоняет `pr-build.yml` на PR, деплой их не дублирует.

⚠️ **Узкое место сборки — диск РАННЕРА, а не VPS.** Симптом обманчив: деплой валится с
`no space left on device`, и первым делом хочется чистить сервер. Смотри на путь в ошибке —
`/var/lib/buildkit/...` живёт на машине, где идёт сборка, то есть на `ubuntu-latest`; VPS
buildkit вообще не запускает, он только тянет готовый образ из GHCR. У раннера на корне
свободно **4.9 ГБ** (замер в логе прогона), а нативная сборка бэкенда (GraalVM +
Gradle-зависимости + бинарник) с выгрузкой слоёв в кэш в них не влезает. Поэтому в
`build-backend` стоит шаг `Free up runner disk`: сносит два самых тяжёлых предустановленных
каталога (android, CodeQL) и даёт 4.9 ГБ → ~20 ГБ. Сносить больше пробовали — семь путей плюс
`docker image prune` давали 32 ГБ, но стоили 71–181с на КАЖДОЙ сборке бэкенда, включая те
(почти все), где всё берётся из кэша и диск не нужен вовсе; прун из тех 27 ГБ дал 1.8. Ловили на прогоне `625a13a`; на VPS в тот момент было свободно 26 ГБ из 54.

⚠️ **Быстрый `build-backend` (~35с–1.5мин) — это норма, а не подозрительный прогон.** Слой
нативного компайла зависит только от `backend/`, который меняется редко, поэтому деплой
фронтовой правки берёт его из кэша (`#15 ... CACHED` в логе). Полный компайл идёт только
после изменений в бэкенде. Отсюда же правило: `cache-to` бэкенда обязан быть `mode=max` —
на `mode=min` builder-стадия не выгружается, кэш перестаёт обновляться, и этот срез
пропадает (пробовали на прогоне `05c222b`, откатили).

⚠️ **`docker system prune -a` на VPS — не безобидная уборка.** Он сносит все неиспользуемые
образы, включая sha-тегированные, а это и есть ручка отката (§5). Чистить — прицельно по
старым тегам, оставляя предыдущий рабочий.

## 5. Обновление и откат

- **Обновление** — само: push/merge в `main` → Actions пересоберёт, прогонит smoke и
  перезапустит. Каждый образ дополнительно тегируется sha коммита.
- **Правка Caddyfile тоже раскатывается сама** — но только потому, что деплой
  **пересоздаёт** `caddy` и `webdav` (`--force-recreate`), а не полагается на `up -d`.
  Причина — инодная привязка bind-маунта одиночного файла: `scp` кладёт новый файл,
  контейнер держит старый инод, и конфиг на диске к боевому процессу отношения не имеет.
  `caddy reload` эту ситуацию **не** чинит и, что хуже, рапортует успехом: он перечитывает
  путь внутри контейнера и получает тот же старый (валидный) файл. На этом потеряли сутки
  на маршруте `/dav`. Перед пересозданием конфиг валидируется в одноразовом контейнере —
  битый Caddyfile валит деплой, а не боевой edge.
  > Рассмотрено и отклонено: переложить конфиги в каталоги (`caddy/Caddyfile`,
  > `webdav/config.yml`) и маунтить каталог — тогда подмена файла видна и хватило бы
  > reload'а. Отклонено: переезд трогает оба compose-файла, scp и доки ради секунды
  > даунтайма на личном сайте, а безусловное пересоздание даёт ту же гарантию одной строкой.
- **Деплой пишет выкаченный `TAG` в `/opt/danchuoworld/.env`** — компоуз читает его сам.
  Иначе образы резолвятся как `${TAG:-latest}`, и **любая** ручная команда `docker compose
  up -d` на VPS (перезапустить один сервис, потрогать edge) тихо откатывает прод на тот
  `:latest`, что лежит на диске, — а он древний: деплой тянет только sha-тег. Проверено
  на себе: ручной рестарт caddy утащил бэкенд на пятнадцать релизов назад, и нигде об этом
  не было сказано ни слова. Диагностика — `docker inspect danchuoworld-backend --format
  '{{.Config.Image}}'`: если там `:latest`, прод крутит не то, что думает.
- **Последнее слово в деплое — за проверкой `/dav` (жёсткой).** Она бьёт в адрес ровно
  как он вписан в читалку и ждёт **401** от WebDAV; 404/308 с HTML означают, что запрос
  дошёл до Next, — деплой краснеет и печатает `ps` и логи caddy. Смысл: весь этот класс
  поломок выглядит как успешная раскатка поверх старого конфига, поэтому подтверждать её
  должен запрос, который проходит только на новом.
- **Релиз на каждую раскатку**: после успешного деплоя workflow создаёт GitHub-релиз
  (тег `prod-<run>`, в имени — версии бэка/фронта) со ссылками на GHCR-образы `:sha`.
  Исходники к релизу не прикладываются — архив исходников GitHub привязывает к тегу сам,
  а образы и так пиновы точным коммитом. Лента релизов = история выкаток и готовые
  ручки отката.
- **Откат**: на VPS `TAG=<старый sha> docker compose -f docker-compose.prod.yml up -d`.
  Откатывается и edge — образ `caddy` теперь тоже пинуется этой sha, так что «вернуть как было»
  возвращает и конфиг, и его модули одним движением.
  Осторожно с Liquibase: если новая версия успела применить миграции, откатываться лучше
  на один шаг.
- **Лимиты и кэш на edge живут в `Caddyfile`** (числа и обоснование — там же в комментариях,
  правило — PRD §8). Менять пороги можно правкой файла: деплой пересоздаёт `caddy` безусловно,
  поэтому новый конфиг применяется без дополнительных телодвижений. Souin при старте пишет
  `You're running Souin with the default storage…` — это ожидаемо: под TTL в 10 секунд
  встроенного in-memory хранилища достаточно, внешнее не заводим.
- **Мониторинг руками**: `ssh -L 8081:localhost:8081 <vps>` → локально
  `curl localhost:8081/q/health`.
